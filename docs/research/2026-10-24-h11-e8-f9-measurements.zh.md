## 2. H11：主智能体自己做 vs 派出去

### 2.1 方法

脚本：`scripts/eval/h11_compare.py`（任务库在 `scripts/eval/tasks.py`，共用部分在 `scripts/eval/common.py`）。

- **任务**：8 个可验收的小 Python 任务，每个是一个临时生成的 git 仓库：实现函数（slugify、时长解析、罗马数字、去重、词频）、修 bug（分页、区间合并）、给命令行加 `--json`。每个任务有：给智能体看的**可见测试**，和只有评测脚本才跑的**隐藏验收测试**（边界情况）。`tests/test_eval_tasks.py` 检查每个任务的起始代码过不了隐藏测试、参考解能过，确保任务可解、验收能失败。
- **配对**：同一任务做两次，每次是全新的临时仓库和全新的无头主智能体（`claude -p`，精简启动：只给 6 个工具、不加载 MCP、系统提示不随目录变，和 ccx 给精简 Claude 子智能体的参数一样）：
  - **self**：“自己用工具做，不要派给别的智能体”；
  - **delegate**：“写一段简短说明，用一次 `ccx run --to codex --model gpt-6-luna --effort low --mode write --new --no-ab --review off --check "python -m pytest -q" --label eval-h11:… "<说明>"` 派出去；ccx 已经重跑了验收命令（看 check 字段）；失败时可以续一次或自己修”。
  - 两种都写同一句“答复前确认验收通过”。两臂的先后顺序每对交替（提示缓存会越跑越热）。
- **判对错**：主智能体结束后，评测脚本把隐藏测试放进仓库跑全部测试；通过 = 做对。delegate 臂的子任务用 `ccx verify <run_id> --ok 1|0 --note "eval-h11 hidden acceptance: …"` 记进账本。
- **量什么**：主智能体的请求数（API 调用次数，按 message id 去重）、所有请求读入的上下文 token 之和、输出 token、主智能体花费、子任务 AE$、墙钟时间、返工（是否续接 / 派完后主智能体自己改了文件 / 子任务的 check 是否失败）。
- **统计**：配对差值的中位数，自助法 95% 区间（4000 次），精确符号检验（双侧）。
- **花费上限**：每开始一个臂之前把已花的钱加一遍，到 `--budget` 就停。

### 2.4 换算到真实主智能体

小模型、精简启动的主智能体每次请求只读约 1.1–1.3 万 token，所以绝对金额很小。真实使用时，`ccx stats --summary` 量到主智能体每次请求重读的中位数是 **219,465 token**。如果主智能体的行为和这里一样，省下的就是“少几次请求 × 每次读多少”：

| 主智能体的行为 | 每个小任务少的请求 | 少读 token | 按 Opus 缓存读价（$0.2/百万） | 减去子任务 | 时间 |
|---|---|---|---|---|---|
| 像 sonnet：信 ccx 的 check | 1 | 21.9 万 | $0.044 | **约省 $0.04** | 多约 16 秒 |
| 像 haiku：自己再验一遍 | 0 | 0 | $0 | **多花约 $0.003** | 多约 18 秒 |

用 Opus 的价格是假设真实主智能体是 Opus；价格表来自 ccx 的路由先验。这一步是外推，不是测量：真实长对话里主智能体可能读更多文件、改主意、或者派出去之后还要多轮沟通。

### 2.5 和 `ccx report` 里“估计节省”的关系

`ccx report` / `ccx stats --summary` 的“估计节省”（当前 $6.82，n = 92）是把**子智能体用掉的 token 按主智能体模型的价格重算**，再减去子任务花费和一个固定的说明开销。这次的配对数据说明，主智能体那边真正省下的是“少发的请求 × 主智能体自己的上下文大小”，和子智能体用了多少 token 关系不大：同一个任务，子智能体读了 7.3–15.2 万 token（中位数约 9.3 万，大多是缓存），主智能体自己做只要 3 次请求、约 3.8 万 token。两个模型算出的数可能差很远，建议以后用“少的请求数 × 主智能体每次请求的上下文”来估计，并用 A/B 自做样本校准（见第 6 节）。这次没有改这个计算。

另外，这次的评测运行（标签 `eval-h11:*`、`eval-f9:*`、`eval-e8:*`）都进了真实账本，会被算进“估计节省”和运行次数；需要排除时按标签过滤。

## 3. E8：两个方向的真实交接

脚本：`scripts/eval/e8_handoff.py`。

### 3.1 方法

- **受控场景**（`run`）：临时仓库里有 4 个互不相关的待实现模块（a/b/c/d）。一个真实的“交出方”主智能体（无头 `claude -p` 或 `codex exec`，会话文件保留在磁盘上）先写编号计划、按顺序做；要么被要求“只做 a、b 就停”，要么在第 20 秒被直接杀掉（`--cut-after 20`，模拟额度用完 / 崩溃）。然后在仓库里跑 `ccx handoff --from-transcript <交出方> --no-model` 生成交接。接手方是另一家的全新智能体（`ccx run --mode read`，Codex 用 luna low，Claude 用 haiku），在**一个空目录**里，只拿到交接文字，不能看文件、不能跑命令，回答 DONE / NEXT / MISSING。标准答案从仓库读：哪些模块真能用、有哪些测试文件。
- **真实会话**（`ask`）：用本会话（Claude Code 桌面版，长会话）的会话文件生成交接，交给 Codex。标准答案是我当时实际所处的位置。
- 判定由我人工对照标准答案，用 `ccx verify` 记进账本。

### 3.2 结果

| # | 方向 | 场景 | 接手方说的位置 | 下一步 | 判定 | 缺了什么 |
|---|---|---|---|---|---|---|
| 1 | Codex → Claude | 做完 a、b 后正常停下 | a、b 和两个测试已完成 | 做 c、d 和测试 | ✓ | 计划没被识别（“no plan list found”）；测试结果只有交出方的一句话 |
| 2 | Claude → Codex | 做完 a、b 后正常停下 | 同上 | 同上 | ✓ | 同上 |
| 3 | Codex → Claude | 第 20 秒被杀，没有收尾消息 | 从“改过的文件”和 git 状态推出 a、b 完成 | 做 c、d | ✓ | “停在哪”为空；a、b 的测试过没过不知道（接手方自己指出了） |
| 4 | Claude（真实长会话）→ Codex | 修复前 | “交接里没有报告任何实验” | 从头开始做 H11/E8/F9 | ✗ | 计划停在第一步（见 bug 2）；实验结果只在工具输出里 |
| 5 | 同上 | 修复后重做 | H11/E8/F9 已完成，正在写报告 | 写报告、跑检查、提 PR | ✓（第一步略过时） | “停在哪”是最后一句聊天文字，比实际进度晚几步；没有实验数据 |

结论：在结构简单的受控场景里，交接只靠代码（不花模型 token）就够接手方说对位置和下一步，连“中途被杀”这种没有收尾消息的情况也行，靠的是“改过的文件 + git 状态”。真实长会话暴露了两个问题：计划被读成了过期状态（已修）；以及交接里没有“结果”——做了什么实验、得了什么数，只在工具输出里，交接不带（没修，见第 5 节）。

注：受控场景里的交出方是无头会话（`codex exec` / `claude -p`），不是桌面版。Codex 的无头会话 `originator = codex_exec`，`--from-transcript codex` 自动挑选时会跳过（它们通常是 ccx 自己的子任务），所以要用 `--session <id>` 指定。Codex 桌面版 → Claude 的真实交接仍没做：本机现有的 Codex 桌面会话都在其他项目里，在那里生成交接会往别的项目写 `.ccx/`，所以没做。

## 4. F9：自带子智能体开 / 关

脚本：`scripts/eval/f9_subagents.py`。

### 4.1 方法

同一个能并行的任务（4 个互不相关的模块，各写一个测试文件），每次一个全新临时仓库，`ccx run --to codex --model gpt-6-luna --effort low --mode write --check "python -m pytest -q"`：开（默认）2 次、关（`--no-subagents`）2 次，再加 1 次“开 + 任务里明确写‘每个模块开一个子智能体并行做’”。是否真的启动了子智能体，用两个独立来源看：ccx 账本的 `codex_children`，以及会话文件——有没有“父会话是这次运行”的子会话文件、这次运行的会话里有没有 `spawn_agent` 调用。codex-cli 0.164 通过一个 `exec`（代码模式）工具去调别的工具，所以要在 `exec` 的输入里找 `tools.spawn_agent(`；会话文件里每次都有 `spawn_agent` 的**工具定义**，不能当成调用（我第一版计数器就是这样数错的，已改）。

### 4.2 结果

| 臂 | 次 | 做对 | AE$ | 秒 | 子智能体（账本 / 子会话文件 / spawn 调用） |
|---|---|---|---|---|---|
| 开 | 1 | ✓ | 0.0035 | 25.1 | 0 / 0 / 0 |
| 关 | 1 | ✓ | 0.0037 | 24.9 | 0 / 0 / 0 |
| 开 | 2 | ✓ | 0.0037 | 21.8 | 0 / 0 / 0 |
| 关 | 2 | ✓ | 0.0024 | 21.8 | 0 / 0 / 0 |
| 开 + 明确要求 | 1 | ✓ | 0.0035 | 25.8 | 0 / 0 / 0 |

原因（从会话文件看到）：codex-cli 0.164 给模型的开发者消息里有一段 `<multi_agent_mode>`，大意是“除非用户或 AGENTS.md / 技能明确要求子智能体、委派或并行，否则不要开子智能体”。中性的任务说明不算“明确要求”；明确要求的那次，luna low 仍然一个补丁写完了全部 4 个模块。所以在本周能用的档位（luna low）上，F9 的“默认开”实际等于关：开/关之间没有可比较的差别，`agents.*` 配置、并发上限和花费看门狗都没被真正用到。

另外，Claude 子智能体的精简启动只给 `Read,Grep,Glob,Edit,Write,Bash` 6 个工具，没有 `Agent` 工具，所以 Claude 那边“开”也开不了（代码注释里有写，文档里的“默认开”没写清这一点）。这次没有跑 Claude 子任务的开/关。

## 6. 局限

- **任务太小、太容易**：两臂全部做对，所以“做对率”和“返工”这次没有区分度（续接 0 次、派完主智能体自己改文件 0 次、子任务 check 失败 0 次）。省不省主要取决于自己做要几次请求：这些任务自己做 3 次就够，派出去最少也要 2 次，能省的空间最多 1 次。更大的任务（自己做要 10 次以上请求）才可能看出更大的差别。
- **主智能体不是真实的**：无头、精简启动、上下文约 1.2 万 token，而真实主智能体是长对话（中位数 21.9 万 token/请求）、模型更强（Opus）。第 2.4 节的金额是外推。
- **样本小**：haiku 8 对、sonnet 6 对；E8 受控 3 次 + 真实 1 个会话；F9 5 次。sonnet 的请求数差别 6/6 一致，有统计意义（p = 0.031），总花费没有。
- **只用了最便宜的档位**：Codex 只用 luna low（本周额度限制），子智能体档位更高时结论可能不同，尤其 F9。
- **提示词会影响结果**：delegate 臂的提示里写了“ccx 已经重跑了验收命令”，这可能让 sonnet 更愿意不复查；haiku 同样的提示仍然复查。这是一个设计选择，不是中立测量。
- **用时**：delegate 的墙钟时间包含子任务（haiku 批的 Codex 子任务本身 13–23 秒，ccx 账本的 `seconds`）。

## 7. 一周持续收集怎么做

1. **每天一小批受控对比**（约 $0.05/天）：
   `python scripts/eval/h11_compare.py run --pairs 4 --tag $(date +%Y%m%d) --budget 0.1`，主智能体模型隔天换 haiku / sonnet；任务库加入 3–4 个“自己做要 8 次以上请求”的中等任务（多文件、要先读代码），否则只能看到“最多省 1 次请求”。
   一周后 `python scripts/eval/h11_compare.py summary` 看全部配对。
2. **真实工作里的 A/B 自做样本**：ccx 已经有这个机制：`ccx config set defaults.ab_self_rate 0.2` 后，路由会随机挑 20% 本该派出去的任务让主智能体自己做，结束时 `ccx ab done <id> --ok 1|0` 记下主智能体自己用了多少（`selfrun` 事件）。一周后和同难度的派出任务比较“主智能体请求数 × 上下文”。
3. **每个派出的任务都记对错**：`ccx verify <run_id> --ok 1|0`，或者至少让会话开始时的 `ccx verify --sweep` 补“大概对”的判定；本次之前账本里只有 2 条人工判定，现在是 31 条（本次 25 条）。
4. **E8**：每次真的换主智能体（额度用完、换工具）时，用 `ccx handoff --from-transcript` 生成交接，接手后第一句话写下“我认为做到哪、下一步”，再对照原会话记一条 `ccx verify`。
5. **F9**：等 Codex 额度允许时，用 `python scripts/eval/f9_subagents.py run --model gpt-6.1-sol --effort medium` 再测一次；如果还是不启动，就在文档里把“默认开”改成“允许，但 Codex 0.164 自己基本不开”。

## 8. 复现

需要已登录的 `claude` 和 `codex` 命令行；运行脚本的 Python 要有 pytest（脚本会把它放在智能体 PATH 的最前面，智能体在临时仓库里用的就是它）。

```
python scripts/eval/h11_compare.py list
python scripts/eval/h11_compare.py run --pairs 8 --tag haiku1 --budget 0.6
python scripts/eval/h11_compare.py run --pairs 8 --tag sonnet1 --lead-model sonnet --lead-effort medium --lead-budget 0.3 --budget 0.5
python scripts/eval/h11_compare.py summary --tag haiku1
python scripts/eval/e8_handoff.py run --from codex --to claude [--cut-after 20]
python scripts/eval/e8_handoff.py run --from claude --to codex
python scripts/eval/f9_subagents.py run --repeat 2 --explicit 1
python scripts/eval/f9_subagents.py summary
```

原始结果在 `.ccx/eval/{h11,e8,f9}/results.jsonl`（不进 git：里面有本机路径）。判定都在 ccx 账本里，按标签 `eval-h11:*`、`eval-e8:*`、`eval-f9:*` 可以查到。
