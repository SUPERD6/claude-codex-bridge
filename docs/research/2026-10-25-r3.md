## Conclusions first

| Question | Verdict | Evidence |
|---|---|---|
| Which arm is more often right | **The same: all right, no difference to test** | self, builtin and ccx all 20/20 (Wilson 0.84–1.0). Discordant pairs 0 : 0 in all three comparisons. The tasks hit the ceiling again |
| Cost per success (CPS) | **Doing it yourself is cheapest** | self $0.045 [0.041, 0.048], builtin $0.069 [0.065, 0.073], ccx $0.071 [0.063, 0.081] (task-level bootstrap). Both ways of delegating cost about 55% more than self (paired +$0.023, sign test p = 0.002) |
| Where ccx beats the built-in sub-agent | **Fewer lead tokens, lower lead spend** | lead tokens median 64k vs 83k: paired −20k [−30k, −13k], p = 0.021; the lead's own spend −$0.0077 [−0.011, −0.003], p = 0.021 |
| Where ccx is worse | **Slower, no cheaper overall, one usability problem** | wall time median 63 s vs 41 s (+26 s [+19, +37], p = 0.002); sub-agent + review cost more ($0.0083 vs $0.0040) and cancel the lead's saving: total −$0.0023 [−0.0066, +0.0011], p = 0.34, ratio 1.02. Rework 3 vs 0 (2 units), 2 of them because the lead piped `ccx run` into `| tail -40`, which cut the run_id off the top of the JSON |
| Versus doing it yourself | **Delegating is worse on every measure** | 3–4× slower (14 s → 41 / 63 s) and *more* lead tokens (49k → 83k / 64k): the leads still read the code before briefing (median 1–2 file reads) and check the result afterwards |
| Build L8? | **No** | Over 42 sub-agent runs, finding/reading files is a median 1.9% [1.2%, 2.4%] of the tokens, at most 5.3%, 1.9% pooled, never above half; a lead doing it itself, 2.2%. The tokens go to fixed overhead (system prompt, tool descriptions) and re-reading the context |
| L5: is memory used? | **Yes, significantly** | memory on 15/24, off 2/24 (discordant 13 : 0, McNemar p = 0.0002). But the note reached the sub-agent's prompt only 20 of 24 times: mem-json's note was never picked (§3) |

**Total spend about $4.05**: in the results files round 3 $3.69 and L5 $0.15; about $0.21 more is not in them (a lead
run stopped mid-pilot, about $0.10; the discarded ccx pilot $0.088; two stopped L5 units $0.007; two format probes
$0.012). Under the $8 cap.

**One-line answer to "why not just use the built-in one"**: on these 10 small-package tasks that need the code read
first and one requirement inferred, a sonnet lead doing the work itself was always right, cheapest and fastest;
handing it to the built-in sub-agent or to ccx was not more often right, only more expensive and slower. Between the
two ways of delegating, ccx saves the lead about 25% of its tokens, but the total spend is the same and it takes 26 s
longer. The value of ccx is not on this kind of task; the cases where it could show (a cheap model that does get things
wrong, a long conversation where the lead's context is expensive, a large repository) were not covered.

## 1. Method

- The lead is always a headless Claude Code (sonnet, effort medium, slim start-up) with the same request; only the
  delegation route differs: ① do it yourself; ② you must hand it to a haiku `worker` with the Agent tool; ③ you must
  hand it out with `ccx run --tradeoff save --review on --context auto`. ② and ③ are told to check the result and send
  it back if needed.
- Every unit: a fresh repo and a fresh throwaway hub; Codex held to luna low, Claude to haiku, A/B self-runs and the
  quota probe off; every run with `--no-ab` and an `eval-r3:` label. ccx's save routing picked **Codex gpt-6-luna low**
  to build and **Claude haiku low** to review in all 20 units (the plan expected deepseek-flash; it was not picked).
- 10 tasks (plan §2) × 2 rounds × 3 arms = 60 units, order randomised within a round (seed 27). The hidden test
  decides, recorded with `ccx verify` in the unit's own hub.
- Statistics: the task is the independent unit. Right/wrong by paired McNemar + Holm (3 comparisons); spend, time and
  lead tokens by the task-level paired difference (the two rounds of a task averaged first): median, bootstrap
  interval, sign test; these are descriptive and not corrected.
- Two design changes after running (verbatim in plan §7): (1) in the pilot the work folder was so deep that the lead's
  session file passed Windows' 260 characters, ccx could not find it and attached no shared context; the real run used
  a short folder and the ccx unit was rerun — 20/20 attached the context in the real run. (2) env-config's hidden test
  also required "unknown environment variables are listed in `_ignored`", which the code does not support; all three
  arms of round 1 failed only that check; it was dropped and `r3.py rescore` scored all 6 env-config units again (the
  first verdicts are kept as `ok_first`: all 6 went from wrong to right).

Notes:

- **Ceiling**: the sonnet lead was 20/20 alone, and haiku and luna were 20/20 with the lead's brief. The delegating
  leads read the relevant code first (median 1–2 file reads) and wrote the "inferred" requirement into the brief (a
  rough keyword check per task: 37 of the 39 briefs that could be checked name it, e.g. `money()`, `redact()`,
  `deprecated_alias`) — the vagueness was absorbed by the lead, and the sub-agent got a clearly specified task. So this
  round cannot tell whether a sub-agent would infer wrongly; it measures the lead + sub-agent as a whole.
- **Why the builtin lead uses more tokens**: not measured separately. Visible: slightly more lead requests (5.5 vs 5),
  and the Agent tool's description and result enter the lead's context; ccx returns a compact JSON.
- **The lost run_id** (rename-slug, round 2): the lead ran `ccx run ... 2>&1 | tail -40`; run_id is the first key of
  the JSON and was cut off. To `ccx resume` it went looking for the run_id — 21 Bash calls in this unit against 3–5 in
  the other ccx units — and on the way **read** (did not write) the person's real hub: its `config.toml` and the last
  two lines of `ledger.jsonl` (`tail -2`). This unit cost $0.169 and 397k lead tokens, the most expensive of the arm.
  ccx prints the run_id only at the top, so a common `tail` loses it.
- The leads wrote some text in Chinese because of the machine's user-level CLAUDE.md; the same for all arms, it does
  not affect the comparison.

## 3. L5 fixed memory test

One side writes the note with `ccx mem add --by <side>` (plus 3 unrelated distractor notes), the other side gets a task
that needs it in a new session (`ccx run --new`); memory off = the distractors only. 6 cases × 2 directions × on/off ×
2 runs = 48 runs, $0.15.

| Case | Off | On | Note in the prompt |
|---|---|---|---|
| mem-errors (error convention) | 0/4 | 3/4 | 4/4 |
| mem-money (money in integer cents) | 0/4 | 4/4 | 4/4 |
| mem-log (one log line per function) | 0/4 | 1/4 | 4/4 |
| mem-dates (day/month/year pitfall) | 0/4 | 3/4 | 4/4 |
| mem-paths (return a Path preference) | 2/4 | 4/4 | 4/4 |
| mem-json (JSON formatting preference) | 0/4 | 0/4 | **0/4** |
| **Total** | **2/24** | **15/24** | 20/24 |

- On vs off: discordant 13 : 0, McNemar p = 0.0002 (a single test). Both directions work: Claude writes → Codex works
  7/12 vs 0/12; Codex writes → Claude works 8/12 vs 2/12.
- Of the 20 runs where the note reached the prompt, 15 were right; mem-log's note arrived 4 times and was followed once
  (the cheap model did not act on it).
- **mem-json never being picked is a ccx problem**: `memory.for_brief` picks notes by shared words; its word list keeps
  trailing punctuation ("JSON." in the brief becomes `json.`, which does not match the note's `json`), does no stemming
  (write / writes) and keeps stop words, so this note shared no word with the brief while the distractors were picked
  for "the". Noted for the session working on `ccx/memory.py`; this PR does not change ccx. After a fix:
  `python scripts/eval/l5_memory.py run --reps 2`.
- Against round 1's 9/9 vs 0/9: this time with distractors and 3 new cases the "on" rate is lower (63%), which is closer
  to a real hub.

## 4. L8: how much of the tokens goes to finding files

| Source | Runs | read_share median | Max |
|---|---|---|---|
| ② haiku worker | 20 | 2.6% | 4.7% |
| ③ ccx builder (luna; Codex approximated) | 22 | 1.1% | 5.3% |
| All | 42 | 1.9% [1.2%, 2.4%] | 5.3% (pooled 1.9%, above half 0 times) |
| For comparison: ① lead doing it itself | 20 | 2.2% | — |

The plan's rule was "pooled and median both above half"; reality is far below, so **the conclusion is: do not build
L8**. Caveat: the tasks are 4–7-file packages and the leads named the files in their briefs; in a large repository with
a brief that names no files the share may be much higher — not measured. Tokens are estimated as characters ÷ 4;
Codex's per-request accounting is approximate.

## 5. Not covered, caveats

- **Small sample, ceiling**: 10 tasks, 60 units, all right — no comparison of success rates could be tested. "Read the
  code first + one inferred requirement" is not hard enough for a sonnet lead or for cheap sub-agents given its brief;
  tasks that would separate them (where the cheap model really fails, multi-step debugging, finding the place in a large
  repository) are still missing.
- ccx was seen only as luna + a haiku review; DeepSeek and Gemini did not appear. One lead model only (sonnet medium).
- The leads were fresh, short sessions. One of ccx's goals — the lead reads less when its long context is expensive —
  was not tested; in a short session the fixed cost of delegating dominates.
- `ccx run` prints the run_id only at the top, so it is lost when the output is cut; under very long paths ccx cannot
  find the lead's session file and `--context` silently attaches nothing. Both are follow-ups; this PR does not change
  ccx.
