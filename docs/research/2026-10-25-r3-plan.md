# Round 3: ccx versus Claude Code's built-in sub-agent, on harder and vaguer tasks (plan)

English · [中文](2026-10-25-r3-plan.zh.md) · 2026-10-25 · written before any real run (changes after the one-task pilot are in §7)

Earlier rounds: [round 1](2026-10-24-seven-cores-ab.md), [round 2](2026-10-25-seven-cores-r2.md). Round 2 found that on
clearly specified medium tasks the cheap model is already near the ceiling (47 of 49). What is still unanswered is the
person's question: **why not just use Claude Code's built-in Agent sub-agent?** This round compares the two directly,
on the same tasks and the same brief, with harder and vaguer tasks. It adds L5 (a fixed memory test) and the evidence
for L8 (how much of a sub-agent's tokens go to finding and reading files).

## 1. Three arms

The lead is always a headless Claude Code (`claude -p`, sonnet, effort medium, slim start-up with the same flags ccx
uses for Claude sub-agents) and gets the same request; only the way the work is handed out differs:

| Arm | The lead is told | Sub-agent |
|---|---|---|
| ① self | do it yourself | none |
| ② builtin | do not edit files; hand it to `worker` with the Agent tool, check what comes back, send it back if needed | `worker`: haiku (defined with `--agents`, tools Read/Grep/Glob/Edit/Write/Bash) |
| ③ ccx | do not edit files; hand it out with `ccx run --tradeoff save --review on --context auto --mode write --new --no-ab --check "python -m pytest -q"`, check, `ccx resume` if needed | the cheap model ccx's save routing picks + the cheapest reviewer from another vendor + the lead's recent work context |

- Every unit gets a fresh repo and a fresh throwaway hub (`CCX_HUB`): A/B self-runs off; Codex held to gpt-6-luna low
  (T2–T4 set to luna low, sol/astra marked unavailable for routing); **Claude held to haiku** (sonnet/opus/fable
  marked unavailable — otherwise a cold hub's `save` picks sonnet medium for a 15-minute task, which is not a cheap
  model; checked); DeepSeek uncapped but every cent recorded; quota probe off. With these settings a cold hub's `save`
  picks deepseek-flash high for this kind of task (checked with `ccx route`).
- ② and ③ get the same "check it, send it back" wording; only the delegation tool differs. The lead's Bash timeout is
  raised to 10 minutes (`BASH_DEFAULT_TIMEOUT_MS`) so `ccx run` is not cut off by the 2-minute default.
- Known asymmetry: ②'s sub-agent is haiku, ③'s is whatever save picks (expected deepseek-flash). These are the default
  shapes of the two routes being compared, not one model under two harnesses; the report says so.

## 2. Tasks (`scripts/eval/tasks_r3.py`, 10)

Each task is a small package of 4–7 files that has to be read first; the change crosses files or has to fit existing
code; and **one requirement has to be inferred from the code** ("report it like the other commands", "upgrade stored
databases the usual way", "like every other log line"). The visible test checks only the main path; the hidden test
checks the inferred requirement too. The inferred part is always visible in the code (a helper, a convention, a
registry, a cache key, the migration list), never a guess.

| id | What has to be inferred |
|---|---|
| cli-stats | a new command registers only once imported in `commands/__init__.py`; help shows its docstring; bad input is a `UserError` (exit 2, `error: ...` on stderr) |
| coupon | amounts go through `money()` (Decimal, half-up to the cent: 1.025 → 1.03); a discount is a negative adjustment, which is how the receipt shows it |
| env-config | environment values go through `coerce()` like file values (`yes` → True, `9000` → int) (an "unknown names go to `_ignored`" check was dropped after the first round, see §7); section names have no underscore, so `APP_DB_POOL_SIZE` is `db.pool_size` |
| rename-user | every write drops the cache keys it makes stale: `("id", uid)`, the old name **and the new one** (`find_by_name` caches a miss as None) |
| csv-report | a report for people reads like the text report: column labels as header, each value through its column's formatter (`1,234.50`, `12.5%`), quoting by the csv module |
| search-api | like `list_items`: archived items hidden, the same paging parameters (clamped to 50, `BadRequest` on bad values), filter before paging, the same envelope; a missing q is a `BadRequest` |
| retry-json | retry exactly like `download`: `RETRY_STATUS` and `ConnectionError`, waits from `backoff.delays` through the injected `self.sleep`, no retry on other 4xx, `ClientError` carries the attempts |
| debug-line | every log line goes through `redact()` (before the `h.`/`q.` prefix is added, or `h.authorization` is not a secret name) and `logfmt()` |
| display-name | "upgrade stored databases the usual way" = append a migration to `MIGRATIONS` (version 3) that fills `display_name` for old rows |
| rename-slug | a renamed function keeps its old name through `compat.deprecated_alias` (a `DeprecationWarning` naming the new one); callers inside the package switch to the new name and no longer warn |

`tests/test_eval_tasks.py` checks that every start fails its hidden test and every reference solution passes.

## 3. Measures and decision rules (fixed in advance)

- **Right or wrong**: the hidden test, recorded in the unit's hub with `ccx verify`.
- **Cost per success (CPS)** = an arm's total spend ÷ its successes, by the
  [conversion method](2026-10-23-token-cost-quantification.md): the lead and the built-in sub-agent from `claude -p`'s
  `total_cost_usd` (split by model, `modelUsage`), ccx's sub-agents and reviews from ccx's ledger in API-equivalent
  dollars (DeepSeek is real money). Interval: bootstrap over tasks (the task is the independent unit).
- **Time** (wall clock), **lead tokens** (the lead's own request contexts + output, built-in sub-agent messages left
  out), **rework** (② extra Agent calls; ③ `ccx resume` calls + extra `ccx run` calls; ccx's own review-and-fix rounds
  reported separately), whether the lead broke the rule and edited files itself.
- **Statistics**: the independent unit is the task; 2 rounds per task. Right/wrong by exact paired McNemar (a pair =
  same task, same round), plus a task-level sign test; spend / time / lead tokens by the task-level paired difference
  (the two rounds of a task averaged first): median, bootstrap 95% interval and sign test. **Three comparisons of the
  success rate (ccx vs builtin is primary; self vs builtin and self vs ccx secondary), Holm-corrected together**; the
  other measures are descriptive and not corrected.
- **Rules**: "ccx is more often right than the built-in sub-agent" needs Holm p < 0.05 in that direction; "cheaper"
  needs the CPS ratio's task-level interval to exclude 1 and the paired spend difference's sign test p < 0.05.
  Otherwise only the direction and interval are reported. With 10 tasks the success rates must differ a lot (about
  6 : 0 discordant pairs) to be significant; this is stated in advance.

## 4. Evidence for L8

For every sub-agent run (②: stream messages whose `parent_tool_use_id` is set; ③: the `events.*.log` of each ccx
builder run, reviews left out) compute `read_share`. Every request re-reads its whole context, so a file read early is
paid for again in every later request: `read_share = Σ_requests (find/read result tokens already in the context,
capped at that request's context) ÷ Σ_requests (context + output)`. Finding/reading = Read/Grep/Glob and shell commands
that only cat/head/ls/find/grep/sed -n/git show; result tokens estimated as characters ÷ 4. Codex's json has no
per-request usage: approximated as "one model call after each tool output", marked approximate. ①'s lead is measured
the same way for comparison.

**Rule**: recommend L8 (impact scope) only if the pooled read_share over all sub-agent runs is above one half and the
median is too; otherwise do not. The report gives the conclusion; L8 is not implemented here.

## 5. L5 fixed memory test (`scripts/eval/l5_memory.py`)

Round 1's 9/9 vs 0/9 turned into a rerunnable fixture: one side writes a preference or a pitfall with
`ccx mem add --by <side>` (shared hub memory); the other side gets, in a new sub-agent session (`ccx run --new`), a
task that needs it; a hidden test says whether it was used.

- 6 cases: round 1's mem-errors, mem-money, mem-log, plus 3 new ones (dates are day/month/year — a pitfall; path
  functions return `pathlib.Path` — a preference; JSON written with `sort_keys` + `indent=2` + a final newline — a
  preference).
- Two directions: Claude writes → Codex luna low works; Codex writes → Claude haiku low works.
- On/off: on = 3 unrelated distractor notes + the note; off = only the 3 distractors. A fresh throwaway hub each.
- Each case × direction × arm twice = 48 runs. Rule: on vs off success, McNemar over 24 pairs (a single test, not
  pooled with §3's correction); also whether the note reached the sub-agent's first prompt (`note_in_prompt`).

## 6. Rules and spend

- Real runs only in throwaway `CCX_HUB`s: the person's ledger, routing data and the H11 trial are not touched; every
  run carries `--no-ab` and an `eval-r3:` / `eval-l5:` label.
- **Total cap $8** (round 3 + L5 together; checked by the scripts before every unit; stop at the cap and report what
  exists). L5 first (estimated < $0.3), then round 3. Round 3 starts with a one-task pilot (all three arms; it counts
  as data unless the design changes afterwards) to price a unit; if the estimate exceeds the cap: first lower the lead's
  effort to low (all three arms together), and if still over, stop and record it before going below the minimum of
  10 tasks × 2 rounds.
- Must finish before 2026-10-31 (11/1–11/7 is the J0 window).
- Scrubbed data (no paths, no session ids) in `docs/research/data/`. Tests and CI never call real CLIs.

## 7. Change log (design changes after running, in order)

- **10/25, after the coupon pilot (all three arms)**: a unit costs self $0.049, builtin $0.074, ccx $0.07–0.09; 60
  units ≈ $4.4, within the cap, so the lead stays at effort medium and the rounds stay at 2.
- In the pilot the ccx arm **did not attach the shared context**: the work folder sat in a very deep temp path, the
  lead's session file's full path passed Windows' 260-character limit and ccx could not find it ("the lead's session
  file was not found"). This is the eval's path; the real run uses a short work folder (`%TEMP%\ccx-r3`), the ccx unit
  was rerun and the context confirmed attached; the self and builtin units do not depend on the path and were kept.
  ccx failing to find session files under very long paths is a follow-up; this PR does not change ccx.
- In a cold hub `save` actually picked Codex luna low as the builder (not deepseek-flash as §1 expected), reviewed by
  haiku. Still "a cheap model + a reviewer from another vendor"; the design is unchanged.
- L8's command classifier got two fixes: Codex's `powershell -Command "..."` wrapper is unwrapped; a `|` inside quotes
  is not a pipe.
- The pilot was stopped once (a script bug: `archive_hub` imported from the wrong module): the stopped lead run (about
  $0.1) and the discarded ccx pilot ($0.088) are not in the results file, so the scripts' stop line went from $8 to
  $7.7 for margin; the report's total adds them back.
- **10/25, after round 1's three env-config units**: all three failed on the same single check — an unknown
  `APP_NOPE_X` in the environment was not listed in `_ignored`. `_ignored` is documented only for unknown file
  sections/keys; "handled like values from the file" does not imply environment names must be listed too, and the
  three leads' approach (look up only the names of known settings) is just as reasonable. That breaks §2's rule (the
  inferred part must be visible in the code), so the check was dropped from the hidden test. `r3.py rescore` scores
  every env-config unit again with the corrected test after the run (the repos stay in the work folder); the first
  verdict stays in the data as `ok_first`. Only these 3 units' results had been seen when this was changed.
