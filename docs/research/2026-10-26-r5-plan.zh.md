# 第 5 轮：大任务（本仓库自己的真实改动）上，派活省不省、更不更对（方案）

[English](2026-10-26-r5-plan.md) · 中文 · 2026-10-26 · 写于正式运行之前（试跑一个任务后的改动记在第 7 节）

前几轮：[第 3 轮](2026-10-25-r3.zh.md)、[第 4 轮](2026-10-26-r4.zh.md)。第 4 轮的结论：小任务上，便宜模型拿用户原话也基本全对；组长不管自己做还是派活，都要发 4–7 次请求，所以派活不省。ccx 想省组长的钱，前提是交出去的工作本身要很多次请求。本轮就测这种任务。

## 1. 任务（`scripts/eval/tasks_r5.py`，10 个）

全部来自本仓库已合并的真实改动。每个任务是**整个仓库**在那次提交的父提交上的样子（ccx 约 1.9 万行代码、约 300 个文件）。说明按 issue 的写法：先讲哪里不对或缺什么，再列出维护者的测试会用到的接口（函数名、返回结构、要原样出现的文字），不写怎么实现。**隐藏测试就是那次提交自己的测试文件**。

| id | 来源 | 要做的 |
|---|---|---|
| brief-words | #116 | 简报挑记忆时，词尾的标点和常见词不算；`ccx run` 输出末尾加 `recap` |
| q-killed-spend | #104 | `q run` 整个被杀后，把卡在 running 的运行补成 interrupted，花费记进账本和队列项 |
| q-resume-session | #105 | `q resume` 接着被杀那次运行的会话续跑，已经做完的不再重做 |
| batch-review-risk | #100 | `ccx batch` 的 plan 里 `review` / `risk` 传到运行 |
| codex-hook-text | #92 | 给 Codex 的 hook 输出不以 `[` / `{` 开头 |
| projects-refresh | #90 | 开局时项目目录过期就在后台重扫，一次只扫一个 |
| dsh-archive | #89 | dsh 会话归档：把 id 加进桌面版的 archived 列表，恢复和续跑时拿掉 |
| quota-stop-log | #62 | 每次判成额度用完都把证据写进 `quota-stops.jsonl`，`ccx quota` 显示最近 5 条 |
| waiting-evals | #59 | 开局“等你决定”的计数不算评测运行 |
| mem-report | #52 | 记下谁用了共享记忆，加 `ccx mem report` |

**筛选**：先从 32 个改了代码又加了测试的提交里，自动挑出“测试在父提交上失败、换上提交里的代码后通过”的 29 个；再去掉只在 Windows 上偶发、依赖时序的修复，去掉断言里精确字符串太多、说明写不清的，去掉和别的任务重叠的，留下 10 个。评测脚本自己再核一遍：10 个任务都是起点失败、参考解通过。

**测试的隔离**：#73 之前的测试，可能没有给每个测试单独设 hub。任务仓库一开始就带上现在的 `tests/conftest.py`（每个测试自己的 hub、工具目录和配置），打分时 `HOME`、`CCX_HUB`、`CODEX_HOME`、`CLAUDE_CONFIG_DIR` 都指向临时目录，不碰本机真实的 hub 和工具配置。

**数据污染**：仓库 2026-10 才公开，在模型的训练截止之后。

## 2. 四组

组长都是全新的无头 Claude Code（sonnet，effort medium，精简启动，同第 3 轮）；只有派活方式不同：

| 组 | 做法 |
|---|---|
| self | 组长自己做 |
| builtin | 组长不许自己改文件，用 Agent 工具交给 haiku `worker`，回来检查，不对就退回 |
| ccx | 组长不许自己改文件，用 `ccx run --tradeoff save --review on --context auto`（自己写 `--check` 跑相关测试）交出去，回来检查，不对就 `ccx resume` |
| direct | 不经组长：`ccx run` 直接交给 Codex gpt-6-luna low，审查开（另一家最便宜的审查者），不给 `--check`（给了就等于告诉它隐藏测试在哪个文件） |

组长的说明里写明：全量测试约 7 分钟，只跑和改动相关的测试。每个单元一个全新仓库和全新临时 hub（同第 3 轮：Codex 只用 luna low，路由不用 sonnet/opus/fable，A/B 自做关闭，DeepSeek 不设上限但记账）。所有运行都带 `--no-ab` 和 `eval-r5:` 标签。

## 3. 指标与判定（事先定）

- **做对率**：隐藏测试全过。
- **每做对一件的花费（CPS）**，算法同第 3 轮：组长和自带子智能体用 `claude -p` 报的 `total_cost_usd`，ccx 用账本的 API 等价美元。
- **组长花费、组长 token、组长请求次数、用时、返工**，算法同第 3 轮。
- **统计**：独立单元是任务；10 个任务 × 2 轮。做对率用配对的精确 McNemar（每对 = 同任务同轮）。主检验是 **ccx vs self**，次要的是 ccx vs builtin、direct vs self、builtin vs self，4 次一起做 Holm 校正。花费、组长花费、用时用任务层配对差的中位数、自助法区间和符号检验，只作描述。
- **判定**：
  - “ccx 比组长自己做省”：ccx 的总花费（组长 + 子智能体 + 审查）比 self 低，任务层配对差的区间不跨 0，且符号检验 p < 0.05。组长自己那部分花费另外报，用来解释原因。
  - “ccx 更对”：Holm 校正后 p < 0.05，且方向为正。
  - “直接交给便宜模型就够”：direct 的做对率不比 self 低超过 2 个任务，且 CPS 低于 self 的一半。
  - 否则只报方向和区间。10 个任务时，做对率要差得很多（不一致对约 6 : 0）才可能显著，这一点事先写明。

## 4. 花费

试跑 1 个任务 × 4 组，按单价估算总花费；**开跑前先告诉用户估算，用户同意后才正式跑**。脚本按结果文件累计花费，到预算上限就停。Codex 只用 luna low。

## 5. 时间

必须在 2026-10-31 前跑完（11/1–11/7 是 J0 窗口，不跑真机）。

## 7. 变更记录（跑之后的设计改动）

- **10/26，试跑 quota-stop-log 四组之后**（算正式数据，第 1 轮的这个任务不再跑）：self 没做对（隐藏测试 1 个没过），用了 18 次组长请求、$0.270；builtin 做对，10 次请求、$0.270；ccx 做对，8 次请求、$0.226（组长 $0.184），`ccx resume` 1 次；direct 做对，$0.037。每个任务四组合计约 $0.80，用时约 16 分钟。
- **估算**：还有 19 个“任务 × 轮”，按试跑单价约 $15；任务大小不一，组长单次上限 $3，按 1.5–2 倍余量估 **$20–30**，预算上限设 **$30**。两个任务并行（`--jobs 2`）约 3 小时。
- 试跑时发现组长按 AGENTS.md 自己 `git commit` 了改动，脚本原来只看未提交的改动，显示改了 0 个文件。改成和起点提交比较（`changed()`），试跑的 4 行已用同样的办法重算（这 4 行的统计里包含了打分时写入的隐藏测试文件，正式运行在打分之前统计）。
- 加了 `--jobs`：一个任务的四组按随机顺序依次跑，最多同时跑 N 个任务。

## 8. 干净的测试环境（r5h 之后；`scripts/eval/preflight.py`）

审查 r5–r5g 的日志发现：每个组长（以及不少 ccx 的 Claude 子智能体）都加载了本人的用户级设置——SessionStart / UserPromptSubmit 钩子（一个注入私人规则文字，两个运行主检出里的 `ccx.py`）、用户级 CLAUDE.md、真实 `~/.claude` 里的自动记忆，以及 `language` 设置。Codex 子智能体用的是真实 CODEX_HOME（其中的 AGENTS.md、带插件 / MCP / 钩子 / 记忆的配置、rules）。会话、工具输出文件和 Codex 信任条目都写进了真实目录；超时只杀直接子进程。今后：

| | 做法 |
|---|---|
| E1 从零开始 | 环境变量按白名单继承；每个单元有自己的 TMP、git 身份、CCX_CONFIG、DSH_HOME。Claude 组长和 ccx 的 Claude 子智能体：`--setting-sources project,local`，设置文件里 `disableAllHooks`、关自动记忆、用 `claudeMdExcludes` 排除用户级 CLAUDE.md / rules，并用拒绝规则挡住真实 `~/.claude` 里的文件、`~/.codex`、`~/.ccx`、真实 hub 和评测检出（子智能体经可选开关 `CCX_CLAUDE_SETTING_SOURCES` / `CCX_CLAUDE_SETTINGS`）。`--claude-isolation config-dir`：每个单元一个全新的 CLAUDE_CONFIG_DIR（需要 `CLAUDE_CODE_OAUTH_TOKEN`）。Codex：本人登录过一次的专用评测 CODEX_HOME（`--codex-home`），加 `CCX_CODEX_ISOLATE=1`（`--ignore-user-config --ignore-rules`、关记忆）。 |
| E2 不留残余 | 每个单元的进程都放进一个 Job Object；单元结束时把留下的、以及命令行里带本单元路径或标签的新进程列出来（连同监听端口），杀掉并记一行日志。删除本单元的 x- 目录、worktree，以及（flags 模式下）以本单元路径命名的 Claude 会话目录。 |
| E3 输入相同 | 每行带指纹：提交、任务文件哈希、`claude` / `codex` / `dsh --version`（每个单元后再查一次）、评测 CODEX_HOME 的文件名和 models_cache 哈希、隔离方式、共享记忆为空。 |
| E4 互不干扰 | 本次运行之外还有别的评测、pytest 或 `ccx run` 在跑时拒绝开始；记录并发数；单元之间再查。 |
| E5 预检 | 任何一项不过就不开始；`--force-unclean` 照跑，并记进每一行。一个金丝雀组长（一次 haiku 请求）必须只看到项目自己的 CLAUDE.md -> AGENTS.md。每行有 `audit`（init 事件：没有钩子、MCP、技能、非内置插件、单元外的记忆路径；没有工具调用提到真实目录、hub 或检出）和 `env_clean`。 |

无法用机制挡住、改为记录的：Bash 仍能读本人能读的任何文件（Windows 上没有 Claude 沙箱），所以每行事后审计；flags 模式下 Claude 仍会写 `~/.claude.json` 的项目条目；评测 CODEX_HOME 由同一次运行的各单元共用（记忆已关，工作目录各不相同）。尚未经真实运行验证：`--setting-sources` 加 `claudeMdExcludes` 是否真能去掉用户级 CLAUDE.md（每次运行前由金丝雀检查）、Windows 上 `//` 拒绝规则路径的写法、dsh 在空 DSH_HOME 下能否工作。

**两轮独立审查之后（同日）修了这些**：拒绝规则改成 Claude Code 在 Windows 上实际匹配的写法（`//c/Users/...`，见权限文档），金丝雀会去读一个被自己规则拒绝的目录来验证；审计能认出 `~`、`$HOME`、`%USERPROFILE%`、`$env:USERPROFILE` 和 Git Bash 的 `/c/...`，并按完整路径段匹配（`1-t-ccx` 不再放过兄弟单元 `1-t-ccx2`）；拒绝清单覆盖所有项目的记忆和会话记录、file-history、sessions、settings 备份和 `~/.agents`；Codex 和 dsh 有单元自己的 home（`CCX_AGENT_HOME`），因为 codex-cli 0.164.0 会从 `$HOME/.agents/skills` 加载用户技能；ccx 的 Claude 子智能体不带技能 / 斜杠命令 / MCP（`CCX_CLAUDE_NO_SKILLS`）；只做检查时不改磁盘，开始运行时如果机器忙或有别的进程用着工作目录，就不清理；模型列表哈希去掉 `fetched_at` / `etag`，允许 Codex 自带的 `skills/.system`；真实 hub 默认值改成 `~/.ccx-hub`；评测 CODEX_HOME 和真实目录重叠时拒绝；Job 里的进程靠关闭 Job 来杀（不会误杀复用了 PID 的进程），端口在杀之前查；子进程先挂起、放进 Job 再恢复；单元之间重新检查提交、任务文件和版本，另有一个每分钟采样一次的监视线程（`codex exec`、`claude -p`、安装版 `ccx run` 都算重任务，shell 和桌面应用本身不算）；每行记录模型、python / pytest / 系统版本和 `tiers.toml` 哈希，单元出错时也有；进程列不出来或机器在单元之间有变化时 `env_clean` 为 false；有杀不掉的进程就停止运行；运行后本人状态有变化时退出码为 4；`summary --tag` 不把不同轮次混在一起。仍然挡不住的：shell（Claude 的 Bash、Codex / dsh 的命令）读本人能读的任何文件、Codex 的 Windows 沙箱用另一个用户跑的命令、flags 模式下的 `~/.claude.json` 条目和 shell 快照。
