# 共享工作上下文：真机 A/B（2026-10-25）

[English](2026-10-25-shared-context-ab.md) · 中文

**问题。** 组长派活时，说明里依赖它和用户在对话里刚定下的事（“按我们说好的”），附上组长最近的工作
（`ccx run --context on`）能不能让子智能体做对？花多少？说明本来就完整时会不会帮倒忙？

**结论（在这个设计下）。** 能，差距很大：一次做对 36/36（带）对 7/36（不带）（配对，McNemar 精确检验 p ≈ 4e-9），
返工 0 次对 29 次，总花费少 63%。中性任务两臂都是 6/6；带上下文在 Codex 上每次多花约 $0.0002，DeepSeek 上看不出差别。
这个设计本身就是对该功能最有利的情形（见下）：它证明机制能把“定下的事”送到，不代表真实工作里有多少活依赖它。

## 设计

- **脚本：** `scripts/eval/shared_context_ab.py`（数据：`docs/research/data/2026-10-25-shared-context-ab.json`）。
- **智能体：** Codex `gpt-6-luna` low（codex-cli 0.164.0）；DeepSeek `deepseek-flash` low，经 `dsh` 0.2.1-rc.3
  （按 token 付费、不设上限、每次都记账）。都用 `--mode write --new --review off --no-escalate --no-subagents`，临时 hub。
- **任务：** 6 个“定过的事”任务，说明只说“按商定的”，答案只在组长的对话里（空列表平均值返回 None；slug 写成
  `Hello_World`；超时 45 秒；函数名 `load_rows`；日期 DD/MM/YYYY；负数量截成 0 并 warning），外加 1 个说明完整的中性任务。
  6 个里有 5 个还有一个用户先提出后又推翻的选项（抛 ValueError、连字符、30 秒、read_rows、抛异常）。
- **组长对话：** 一个写好的 Claude Code 会话文件（约 10 轮：要求、无关闲聊、被推翻的选项、最终决定、计划更新、一次编辑），
  通过 `CCX_LEAD_SESSION` 找到。项目文件夹和放这些文件的文件夹分开，子智能体到处翻也翻不到。
- **两臂：** `--context on` 对 `--context off`；同任务、同智能体、同一次重复为一对；重复 3 次 → 7 × 2 家 × 3 = 42 对、84 次运行。
- **对错：** 子智能体看不到的隐藏 pytest 测试。做错的给一轮返工（`ccx resume`），附上失败的断言行，就像组长会退回去那样；
  **返工率** = 需要返工的比例。花费 = 本次 + 返工（账本，按 API 价格；DeepSeek 是真钱）。

## 结果

| 范围 | 臂 | 一次做对 | 返工 | 返工一轮后做对 | 花费 |
|---|---|---|---|---|---|
| 定过的事，两家合计 | 不带 | 7/36（19%，CI 10–35%） | 29 | 23/36 | $0.2063 |
| | **带** | **36/36**（100%，CI 90–100%） | **0** | 36/36 | **$0.0768** |
| Codex luna low | 不带 | 2/18 | 16 | 11/18 | $0.0632 |
| | 带 | 18/18 | 0 | 18/18 | $0.0430 |
| DeepSeek flash low | 不带 | 5/18 | 13 | 12/18 | $0.1432 |
| | 带 | 18/18 | 0 | 18/18 | $0.0339 |
| 中性任务，两家合计 | 不带 | 6/6 | 0 | 6/6 | $0.0109 |
| | 带 | 6/6 | 0 | 6/6 | $0.0122 |

配对：只有带的做对 29 对，只有不带的做对 0 对（Codex 16 / 0，p = 3e-5；DeepSeek 13 / 0，p = 2.4e-4）。按任务，不带：
1/6、1/6、1/6、0/6、3/6、1/6（日期格式一半猜对了）；带：每个都 6/6。

这些短对话附带的上下文是 1130–1388 字符（约 300–350 token）。

**整个 A/B 花费 $0.3063**（API 价格）；DeepSeek 真钱 $0.1856，Codex 折合 API $0.1207（订阅内）。

## 不带上下文时它们怎么做的

不带上下文时，两家的做法都算得体，只是无从得知：要么停下来问（空列表、日期格式、函数名：“工作区里没有之前约定的记录”），
要么合理地猜错（超时 10 秒、`load_csv`、小写加连字符、负数量抛 ValueError）。即使把失败的断言退回去，29 次返工里还有 13 次没改对
（多是先停下来问、再误读断言，或者坚持自己的约定）。

## 局限——引用数字前先读

- **设计上就是最有利情形。** 每个“定过的事”任务不知道那个决定就做不对；真实派活里大多数说明会写清要什么。真实使用中该看的是
  “说明依赖对话”的比例，这里没测。
- **组长对话短而干净**（约 10 轮，决定用直白的话写在末尾附近）。真实对话又长又杂；提取器只保留最近 5 条要求和 8 条按关键词挑出的
  “定下来的句子”。不用这些词表达的决定、或早于最近 5 条要求的决定可能漏掉。在真实会话上看过（对本项目统筹会话跑 `ccx peek`），
  两种噪音都有：进度句子被当成“定下来的”，以及（本 PR 里已修）项目外的临时脚本和表格行。
- **组长是写出来的会话文件，子智能体是真的。** `ccx peek` 和每轮 hook 那一行在真实的 Claude、Codex、dsh 会话文件上验过，但没进 A/B。
- **每家一个模型、低强度、重复 3 次。** 分家的 95% 区间很宽。
- **没测：** Codex 或 DeepSeek 当组长（只用了 Claude 组长会话）；桌面端真实会话里每轮 hook 那一行（Codex 桌面端 hook 仍未验证，H7）。

## 复现

```bash
CCX_DSH_BIN=/path/to/dsh.cmd python scripts/eval/shared_context_ab.py run --out /tmp/scab --reps 3 --jobs 6
python scripts/eval/shared_context_ab.py summary --out /tmp/scab
```
