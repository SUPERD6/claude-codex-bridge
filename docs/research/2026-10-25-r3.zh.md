## 先说结论

| 问题 | 判定 | 证据 |
|---|---|---|
| 三组谁更对 | **一样，全对，分不出来** | self、builtin、ccx 都是 20/20（Wilson 0.84–1.0）。不一致对 0 : 0，三次比较都没有可检验的差别。任务又碰到了天花板 |
| 每做对一件的花费（CPS） | **自己做最便宜** | self $0.045 [0.041, 0.048]，builtin $0.069 [0.065, 0.073]，ccx $0.071 [0.063, 0.081]（任务层自助法区间）。两种派活都比自己做贵约 55%（配对差 +$0.023，符号检验 p = 0.002） |
| ccx 比自带子智能体好在哪 | **组长 token 少、组长花费少** | 组长 token 中位数 6.4 万对 8.3 万：配对差 −2.0 万 [−3.0 万, −1.3 万]，p = 0.021；只算组长的花费 −$0.0077 [−0.011, −0.003]，p = 0.021 |
| ccx 比自带子智能体差在哪 | **慢，总花费不省，有一次可用性问题** | 用时中位数 63 秒对 41 秒（+26 秒 [+19, +37]，p = 0.002）；子智能体 + 审查更贵（$0.0083 对 $0.0040），把组长省下的抵掉了：总花费差 −$0.0023 [−0.0066, +0.0011]，p = 0.34，比值 1.02。返工 3 次对 0 次（2 个单元），其中 2 次是组长把 `ccx run` 的输出接了 `| tail -40`，run_id 在 JSON 第一行被截掉，只好去找 |
| 和自己做比 | **派活全面更差** | 比自己做慢 3–4 倍（14 秒 → 41 / 63 秒），组长 token 反而更多（4.9 万 → 8.3 万 / 6.4 万）：组长派活前照样自己读代码（读文件中位数 1–2 次），派完还要检查 |
| L8 要不要做 | **不做** | 42 次子智能体运行里找文件/读文件只占 token 的中位数 1.9% [1.2%, 2.4%]，最高 5.3%，合计 1.9%，没有一次过半；组长自己做时也只占 2.2%。token 几乎都花在固定开销（系统提示、工具说明）和反复重读上下文上 |
| L5 记忆有没有用上 | **有，显著** | 开记忆 15/24、关记忆 2/24（不一致对 13 : 0，McNemar p = 0.0002）。但笔记只有 20/24 次进了子智能体的提示：mem-json 那条 4 次全没选上（见 §3） |

**总花费约 $4.05**：结果文件里第 3 轮 $3.69、L5 $0.15；另有约 $0.21 没进结果文件（试跑中途停掉的一次组长运行约 $0.10，作废的 ccx 试跑 $0.088，停掉的两次 L5 $0.007，两次格式探测 $0.012）。没超过 $8 上限。

**一句话回答“为什么不直接用自带的”**：在这批 10 个“要先读懂代码、有一处要推断”的小包任务上，sonnet 组长自己做全对、最便宜、最快；派给自带子智能体或 ccx 都不更对，只更贵更慢。两种派活之间，ccx 让组长少用约 25% 的 token，但总花费一样、慢 26 秒。只能说 ccx 的价值不在这类任务上；能体现它的场景（便宜模型会错、组长上下文很贵的长对话、大仓库）本轮没覆盖。

## 1. 怎么测的

- 组长都是无头 Claude Code（sonnet，effort medium，精简启动），拿到同一句需求；只有派活方式不同：①自己做；②必须用 Agent 工具交给 haiku 的 `worker`；③必须用 `ccx run --tradeoff save --review on --context auto` 交出去。②③ 都被要求检查结果、不对就退回。
- 每个单元一个全新仓库 + 全新临时 hub：Codex 只用 luna low，Claude 只用 haiku，A/B 自做关闭，额度探测关闭；所有运行带 `--no-ab` 和 `eval-r3:` 标签。ccx 的 save 路由 20 次都选了 **Codex gpt-6-luna low** 做、**Claude haiku low** 审（方案里预计是 deepseek-flash，实际不是）。
- 10 个任务（见方案 §2）× 2 轮 × 3 组 = 60 个单元，组内顺序随机（种子 27）。隐藏测试判定，用 `ccx verify` 记进单元自己的 hub。
- 统计：独立单元是任务。做对率配对 McNemar + Holm（3 次比较）；花费、用时、组长 token 用任务层配对差（同任务两轮先取平均）的中位数、自助法区间、符号检验，这些不做校正，只作描述。
- 跑之后改过两处设计（方案 §7 有原文）：(1) 试跑时工作目录路径太深，组长会话文件超过 Windows 260 字符，ccx 找不到它、没附上共享上下文；正式运行改短目录，ccx 那次重跑。正式运行 20/20 都附上了。(2) env-config 的隐藏测试原来还查“环境里未知的变量要记进 `_ignored`”，这条从代码推不出来，第 1 轮三组都只错在这条，删掉后用 `r3.py rescore` 重判全部 6 个 env-config 单元（原判定在数据的 `ok_first` 里：6 个都从错变对）。

配对比较（任务层，10 个任务）：

| 比较 | 做对 | 总花费差 | 组长 token 差 | 用时差 |
|---|---|---|---|---|
| builtin → ccx（主检验） | 0 : 0，无法检验 | −$0.0023 [−0.0066, +0.0011]，p = 0.34 | −2.0 万 [−3.0, −1.3 万]，p = 0.021 | +26 秒 [+19, +37]，p = 0.002 |

（p 是 10 个任务的符号检验，10 个任务方向全一致时最小是 0.002；没有做多重比较校正。）

要注意的：

- **天花板**：sonnet 组长自己做 20/20，haiku 和 luna 拿着组长写的简报也全对。组长派活前都自己读了相关代码（读文件中位数 1–2 次），把“要推断的那条”直接写进了简报（按每个任务的关键词粗查，39 份可查的简报里 37 份点出了，如 `money()`、`redact()`、`deprecated_alias`）——“模糊”被组长消化掉了，子智能体拿到的是说清楚的任务。所以本轮测不出“子智能体会不会推断错”，测到的是“组长 + 子智能体”整体。
- **为什么 builtin 组长 token 更多**：没有单独测。能看到的是 builtin 组长请求数略多（5.5 对 5），Agent 工具本身的说明和返回结果也进组长上下文；ccx 的返回是一个压缩过的 JSON。
- **丢 run_id 那次**（rename-slug 第 2 轮）：组长执行 `ccx run ... 2>&1 | tail -40`，run_id 是输出 JSON 的第一个键，被截掉了；为了 `ccx resume` 它去找 run_id，这个单元一共 21 次 Bash（别的 ccx 单元 3–5 次），途中**只读地**看了用户真实 hub 的 `config.toml` 和 `ledger.jsonl` 最后两行（`tail -2`），没有写入。这一个单元花了 $0.169、39.7 万组长 token，是全组最贵的。说明 ccx 的输出把 run_id 只放在开头，被常见的 `tail` 截断后就找不回来。
- 组长受本机用户级 CLAUDE.md 影响用中文写了部分说明；三组一样，不影响比较。

## 3. L5 记忆固定用例

一边 `ccx mem add --by <一边>` 写下笔记（加 3 条无关的干扰笔记），另一边新会话（`ccx run --new`）接到用得上它的任务；关记忆 = 只有干扰笔记。6 个用例 × 2 个方向 × 开/关 × 2 次 = 48 次，$0.15。

| 用例 | 关 | 开 | 笔记进了提示 |
|---|---|---|---|
| mem-errors（报错约定） | 0/4 | 3/4 | 4/4 |
| mem-money（金额用整数分） | 0/4 | 4/4 | 4/4 |
| mem-log（每个函数记一行日志） | 0/4 | 1/4 | 4/4 |
| mem-dates（日/月/年的坑） | 0/4 | 3/4 | 4/4 |
| mem-paths（返回 Path 的偏好） | 2/4 | 4/4 | 4/4 |
| mem-json（JSON 写法的偏好） | 0/4 | 0/4 | **0/4** |
| **合计** | **2/24** | **15/24** | 20/24 |

- 开 vs 关：不一致对 13 : 0，McNemar p = 0.0002（单独一次检验）。两个方向都有效：Claude 记 → Codex 做 7/12 对 0/12；Codex 记 → Claude 做 8/12 对 2/12。
- 笔记进了提示的 20 次里对了 15 次；mem-log 进了 4 次只用上 1 次（便宜模型没照做）。
- **mem-json 全没选上是 ccx 的问题**：`memory.for_brief` 按共同词挑笔记，词表保留末尾标点（简报里的 “JSON.” 变成 `json.`，和笔记里的 `json` 对不上）、不做词形还原（write / writes）、也不去停用词，于是这条笔记和简报一个共同词都没有，干扰笔记反而靠 “the” 被选上。已经留言给正在改 `ccx/memory.py` 的会话；本 PR 不改 ccx 代码。修了之后重跑：`python scripts/eval/l5_memory.py run --reps 2`。
- 和第 1 轮的 9/9 对 0/9 比：这次加了干扰笔记和 3 个新用例，开记忆的做对率低了（63%），这更接近真实 hub 的情况。

## 4. L8：找文件占多少 token

| 来源 | 运行数 | read_share 中位数 | 最高 |
|---|---|---|---|
| ② haiku worker | 20 | 2.6% | 4.7% |
| ③ ccx 构建者（luna，Codex 用近似算法） | 22 | 1.1% | 5.3% |
| 合计 | 42 | 1.9% [1.2%, 2.4%] | 5.3%（合计 1.9%，过半 0 次） |
| 对照：① 组长自己做 | 20 | 2.2% | — |

方案定的规则是“合计和中位数都过半才做”，实际差得很远，**结论：不做 L8**。保留的话：任务都是 4–7 个文件的小包，组长又在简报里点了文件名；大仓库、简报不点文件的情况下比例可能高很多，本轮没测。token 按字符数 ÷ 4 估，Codex 的逐次请求是近似。

## 5. 没覆盖、要保留的

- **样本小、天花板**：10 个任务、60 个单元全对，做对率的比较一次都没法检验。“要先读代码 + 一处推断”对 sonnet 组长和便宜子智能体都不够难；能拉开差距的任务（便宜模型确实会错的、要多步调试的、大仓库里找位置的）还没有。
- ccx 只测到了 luna + haiku 审这一种组合；DeepSeek、Gemini 没有出现。组长只有 sonnet medium 一种。
- 组长都是新开的短会话。ccx 的设计目标之一是长对话里组长上下文很贵时少读东西，这一点本轮没测；短会话里派活的固定开销占大头。
- `ccx run` 输出的 run_id 只在开头，一截断就丢；ccx 在超长路径下找不到组长会话文件、`--context` 悄悄什么都不附。这两条是后续可修的问题，本 PR 不改 ccx。
