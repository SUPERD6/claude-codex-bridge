# 第 3 轮：ccx 对 Claude Code 自带子智能体，在更难、说得模糊的任务上（方案）

[English](2026-10-25-r3-plan.md) · 中文 · 2026-10-25 · 写于任何正式运行之前（试跑一个任务后的改动记在第 6 节）

前两轮：[第 1 轮](2026-10-24-seven-cores-ab.zh.md)、[第 2 轮](2026-10-25-seven-cores-r2.zh.md)。第 2 轮的结论是：说明写清楚的中等任务上，便宜模型已经接近天花板（49 次对 47 次）。还没回答的问题是用户问的那句：**为什么不直接用 Claude Code 自带的 Agent 子智能体？** 本轮在同样的任务、同样的简报上直接比，任务换成更难、更模糊的。另加 L5（记忆效果固定用例）和 L8 的判断依据（子智能体的 token 有多少花在找文件/读文件上）。

## 1. 三组

组长都是无头的 Claude Code（`claude -p`，sonnet，effort medium，精简启动，和 ccx 起 Claude 子智能体用的参数一样），拿到同一句用户需求，只有“怎么分出去”不同：

| 组 | 组长被告知 | 子智能体 |
|---|---|---|
| ① self | 自己做 | 无 |
| ② builtin | 不许自己改文件；用 Agent 工具交给 `worker`，回来后检查，不对就再派一次 | `worker`：haiku（`--agents` 定义，工具 Read/Grep/Glob/Edit/Write/Bash） |
| ③ ccx | 不许自己改文件；用 `ccx run --tradeoff save --review on --context auto --mode write --new --no-ab --check "python -m pytest -q"` 交出去，回来后检查，不对就 `ccx resume` | ccx 按 save 路由选的便宜模型 + 另一家最便宜的审查 + 组长最近的工作上下文 |

- 每个单元一个全新仓库、一个全新临时 hub（`CCX_HUB`）：A/B 自做关闭；Codex 只用 gpt-6-luna low（T2–T4 都改成 luna low，sol/astra 对路由标记不可用）；**Claude 只用 haiku**（sonnet/opus/fable 对路由标记不可用——不这样的话，冷 hub 里 `save` 对 15 分钟任务会选 sonnet medium，就不是“便宜模型”了，试过）；DeepSeek 不设上限但照样记账；关额度探测。冷 hub 下 `save` 对这类任务选的是 deepseek-flash high（试过 `ccx route`）。
- ②、③ 的“检查、退回”话术一样；只有派活的工具不同。组长 Bash 超时调到 10 分钟（`BASH_DEFAULT_TIMEOUT_MS`），免得 `ccx run` 被 2 分钟默认超时打断。
- 已知不对称：② 的子智能体是 haiku，③ 是 save 选的（预计 deepseek-flash）。这正是要比的两条路的默认样子，不是同一个模型下的比较；报告里照写。

## 2. 任务（`scripts/eval/tasks_r3.py`，10 个）

每个任务是 4–7 个文件的小包，必须先读代码；改动要跨文件或要配合已有代码；**需求里有一处要从代码推断**（“像其他命令那样报错”“按老办法升级”“和其他日志行一样”），可见测试只查主路径，隐藏测试连推断的那条一起查。推断的那条都能从现有代码里看出来（一个辅助函数、一个约定、一个注册表、一个缓存键、迁移列表），不是瞎猜。

| id | 要推断的 |
|---|---|
| cli-stats | 新命令要在 `commands/__init__.py` 里导入才会注册；要有 docstring 才在 help 里有说明；坏输入用 `UserError`（退出码 2、stderr 写 `error: ...`） |
| coupon | 金额都过 `money()`（Decimal、四舍五入到分，1.025 → 1.03）；折扣是负的调整项，收据就是这样显示的 |
| env-config | 环境变量的值和文件的值一样过 `coerce()`（`yes` → True、`9000` → int）（原来还查“未知名字进 `_ignored`”，第一轮后删掉，见第 7 节）；段名没有下划线，`APP_DB_POOL_SIZE` 是 `db.pool_size` |
| rename-user | 每次写都要清掉变旧的缓存键：`("id", uid)`、旧名字，**还有新名字**（`find_by_name` 会把“没找到”也缓存成 None） |
| csv-report | 给人看的报表像文本报表一样：表头用列标签，每个值过该列的格式函数（`1,234.50`、`12.5%`），用 csv 模块加引号 |
| search-api | 和 `list_items` 一样：隐藏已归档的、同样的分页参数（夹到 50、坏值报 `BadRequest`）、先过滤再分页、同样的返回结构；缺 q 报 `BadRequest` |
| retry-json | 和 `download` 一样重试：`RETRY_STATUS` 和 `ConnectionError`、等待时间来自 `backoff.delays` 并走注入的 `self.sleep`、其他 4xx 不重试、`ClientError` 带尝试次数 |
| debug-line | 每行日志都先过 `redact()`（要在加 `h.`/`q.` 前缀之前，否则 `h.authorization` 不算密钥名）再过 `logfmt()` |
| display-name | “按老办法升级已存的库” = 在 `MIGRATIONS` 末尾加一个新迁移（版本 3），给旧行补 `display_name` |
| rename-slug | 改名的函数用 `compat.deprecated_alias` 保留旧名（`DeprecationWarning` 里点名新函数）；包内调用方改用新名，不再触发警告 |

`tests/test_eval_tasks.py` 检查每个任务起始代码过不了隐藏测试、参考解能过。

## 3. 指标与判定（事先定）

- **做对率**：隐藏测试，用 `ccx verify` 记进该单元的 hub。
- **每做对一件的花费（CPS）** = 该组总花费 ÷ 做对件数，按[折算法](2026-10-23-token-cost-quantification.zh.md)：组长和自带子智能体用 `claude -p` 报的 `total_cost_usd`（按模型拆分，`modelUsage`），ccx 子智能体和审查用 ccx 账本的 API 等价美元（DeepSeek 是真钱）。区间：按任务自助抽样（任务是独立单元）。
- **用时**（墙钟）、**组长 token**（组长自己每次请求的上下文 + 输出之和，不含自带子智能体的消息）、**返工**（② 多派的 Agent 次数；③ `ccx resume` 次数 + 多起的 `ccx run` 次数；另报 ccx 自己审查后改一轮的次数）、组长有没有违规自己改文件。
- **统计**：独立单元是任务；每任务 2 轮。做对率用配对的精确 McNemar（每对 = 同任务同轮），另报任务层符号检验；花费/用时/组长 token 用任务层配对差（先对同任务两轮取平均）的中位数、自助法 95% 区间和符号检验。**做对率的比较 3 次（ccx vs builtin 是主检验，self vs builtin、self vs ccx 是次要），一起做 Holm 校正**；花费等指标的比较另算，不校正，只作描述性证据。
- **判定**：“ccx 比自带子智能体更对”要 Holm p < 0.05 且方向为正；“更省”要 CPS 的任务层区间不跨 1 倍比值、且配对花费差的符号检验 p < 0.05。否则只报方向和区间。n = 10 个任务时，做对率要差得很大（不一致对至少约 6 : 0）才可能显著，这一点事先写明。

## 4. L8 的判断依据

每次子智能体运行（② 是 stream 里 `parent_tool_use_id` 非空的消息；③ 是 ccx 每个构建运行的 `events.*.log`，审查不算）算 `read_share`：每次请求都会重读整个上下文，所以早读进来的文件在后面每次请求里都要再付一次。`read_share = Σ_请求（此前读进来的找文件/读文件结果 token，不超过该次上下文）÷ Σ_请求（上下文 + 输出）`。找文件/读文件 = Read/Grep/Glob，以及只做 cat/head/ls/find/grep/sed -n/git show 之类的 shell 命令；结果的 token 按字符数 ÷ 4 估。Codex 的 json 没有逐次请求的用量，用“每个工具输出之后约一次模型调用”近似，标注为近似。①的组长也算一遍作对照。

**判定**：所有子智能体运行合计（pooled）的 read_share 过半、且中位数过半，才建议做 L8（影响范围）；否则不建议。报告只给结论，不实现 L8。

## 5. L5 记忆固定用例（`scripts/eval/l5_memory.py`）

把第 1 轮 9/9 对 0/9 的做法整理成能重跑的固定用例：一边用 `ccx mem add --by <一边>` 记下一条偏好或坑（共享 hub 记忆），另一边新开一个子智能体会话（`ccx run --new`）接到一个用得上它的任务，隐藏测试判定有没有用上。

- 用例 6 个：第 1 轮的 mem-errors、mem-money、mem-log，加 3 个新的（日期是日/月/年的坑、路径函数返回 `pathlib.Path` 的偏好、JSON 写法 `sort_keys` + `indent=2` + 结尾换行的偏好）。
- 两个方向：Claude 记 → Codex luna low 做；Codex 记 → Claude haiku low 做。
- 开/关：开 = 3 条无关的干扰笔记 + 那条笔记；关 = 只有 3 条干扰笔记。各用一个全新临时 hub。
- 每个用例 × 方向 × 开关跑 2 次 = 48 次。判定：开 vs 关的做对率，McNemar（24 对，单独一次检验，不和第 3 节合并校正）；另报笔记有没有进子智能体的第一条提示（`note_in_prompt`）。

## 6. 规则与花费

- 真机只在临时 `CCX_HUB` 里跑，不碰用户的账本、路由数据和 H11 试用；所有运行带 `--no-ab` 和 `eval-r3:` / `eval-l5:` 标签。
- **总花费上限 $8**（第 3 轮 + L5 合计，脚本每个单元前检查，到了就停，按已有结果出报告）。先跑 L5（预估 < $0.3），再跑第 3 轮。第 3 轮先试跑一个任务三组（算正式数据，除非之后改了设计），按单价估算；估算超过上限时，按优先级减：先把组长 effort 降为 low（三组一起改），仍超就减少任务，但不少于 10 个任务 × 2 轮的下限之前先停下记录。
- 必须在 2026-10-31 前跑完（11/1–11/7 是 J0 窗口）。
- 脱敏数据（不含路径、会话 id）放 `docs/research/data/`。测试和 CI 不调用真 CLI。

## 7. 变更记录（跑之后的设计改动，按时间）

- **10/25，试跑 coupon 三组之后**：单价 self $0.049、builtin $0.074、ccx $0.07–0.09，60 个单元估约 $4.4，在上限内，组长 effort 保持 medium，轮数保持 2。
- 试跑里 ccx 组**没附上共享上下文**：工作目录在很深的临时路径下，组长会话文件的完整路径超过 Windows 的 260 字符，ccx 找不到它（`the lead's session file was not found`）。这是评测路径造成的，正式运行改用短工作目录（`%TEMP%\ccx-r3`），ccx 那一次重跑并确认附上了；self、builtin 两次与路径无关，保留。ccx 在超长路径下找不到会话文件这件事记为后续问题，本 PR 不改 ccx 代码。
- 冷 hub 里 `save` 实际选的构建者是 Codex luna low（不是第 1 节估计的 deepseek-flash），审查者 haiku。仍然是“便宜模型 + 另一家审查”，设计不变。
- L8 的命令识别补了两处：拆开 Codex 的 `powershell -Command "..."` 包装；引号里的 `|` 不当管道。
- 试跑中途停过一次（脚本 bug，`archive_hub` 引用错了模块）：停掉的组长运行约 $0.1 和作废的 ccx 试跑 $0.088 没进结果文件，所以脚本的停止线从 $8 降到 $7.7 留余量，报告里的总花费会把它们加回去。
- **10/25，第 1 轮 env-config 三组之后**：三组都只错在同一条——环境里未知的 `APP_NOPE_X` 没进 `_ignored`。`_ignored` 的说明只讲“文件里的未知段/键”，“和文件的值一样处理”推不出环境变量也要记进去；三个组长的做法（只看已知设置对应的变量名）同样合理。这条违反第 2 节“推断的那条必须能从代码看出来”的规则，所以从隐藏测试里删掉。脚本加了 `r3.py rescore`：跑完后用改正后的测试重判 env-config 的全部单元（仓库都留在工作目录里），原判定留在数据的 `ok_first` 字段。改动时只看到了这 3 个单元的结果。
