## Conclusions first

> **Follow-up (§7)**: after #126–#129, ccx as the skill now teaches it ("ccx2") was right 39/40 over two runs at
> $0.116–$0.131 per success, the cheapest way to delegate with a lead and faster than the built-in sub-agent. The
> table below is the first run, before those fixes.

| Question | Verdict | Evidence |
|---|---|---|
| Is ccx cheaper than the lead doing it? | **No** | cost per success: self $0.211, ccx $0.248; task-level paired difference +$0.009 [−0.041, +0.057], p = 0.75 |
| Is ccx more right? | **No** | self 19/20, ccx 17/20 (discordant 2 : 0, p = 0.5) |
| Does delegating cut the lead's spend? | **Yes, but ccx's saving goes to the sub-agent and review** | lead tokens, median: self 382k, ccx 175k (paired −176k, p = 0.002), built-in 107k; lead requests 13 / 8 / 6 |
| Built-in sub-agent | **Cheapest with a lead on large tasks, as right** | 19/20, $0.155 per success; vs self paired −$0.037 [−0.100, −0.017] (p = 0.11); vs ccx $0.044 cheaper [+0.002, +0.112] (p = 0.021) |
| Is a cheap model alone (no lead) enough? | **About 1/4 of the spend, but 3 units fewer right: the pre-set bar was missed** | direct 16/20, $0.054 per success; the bar was "no more than 2 fewer right than self at under half the spend": spend met, correctness missed by one |
| Speed | **ccx slowest** | wall time, median: self 96 s, built-in 286 s, direct 224 s, ccx 464 s (vs self paired +320 s, p = 0.002) |

**Total spend $12.32** (results file $12.05 plus the dropped pilot units $0.27), against a $30 cap.

**In one line**: on large tasks a lead doing the work itself does make many requests (median 13), and delegating cuts the
lead's requests and tokens sharply, which confirms round 4's reasoning. On money, though, **Claude Code's built-in
sub-agent** did best: the sub-agent is haiku, its result goes straight into the lead's context, and there is no extra
review round. ccx's extra spend and time sit mostly in the review and the fix rounds it triggers, and on these tasks the
review did not make anyone more right.

## 4. What is fixed (no default or skill text changed; #122 was in before this round, #123 and #124 came from its records)

1. `ccx resume` keeps the run's label, acceptance command and risk: a lead's fix round was never checked (#122).
2. Claude sub-agents' result schema requires only `status` and `summary`: 10 runs in rounds 4–5 re-sent a result
   missing an optional key, 51 extra turns (#122).
3. `ccx resume` refuses while the session is still busy (#123).
4. Shared work context keeps the person's newest ask up to 3000 characters (#123).
5. Sub-agent rules no longer forbid the sub-agents a task asks for; a Windows shell note for Codex (#124). On
   brief-words: with the fix 4/4 right and all `done`; with only the encoding note 1 `blocked` and 2 `partial`.

**This round ran without #123 and #124**: 2 of ccx's 3 failures relate directly to what they fixed (the cut, the
collision); 1 of direct's 4 (the contradicting rules). Whether ccx now catches up with the built-in sub-agent needs a
re-run of the ccx arm.

## 5. Next

1. **The review raises `[must]` only for the spec's stated requirements**; robustness and edge cases go to `[note]`.
   This changes the review's default behaviour, so it is decided by measurement (the confirmation run; the H11
   trial was voided on 2026-10-26).
2. **Lead side (agent-delegate skill, after the confirmation run)**: large tasks with `ccx run --bg` plus `ccx show`; paste the
   interface part of the person's words into the brief as is; do not ask the sub-agent to commit.
3. **Re-run the ccx and direct arms with #123 and #124** (20 units each, about $5) to see what the fixes changed.
4. Keep recommending a cheap model straight away for small, clear tasks; on large tasks the built-in sub-agent is the
   cheapest way to delegate today, and ccx's value is other vendors' models, accounting and undo.

**What each step showed**

1. **r5c, lean recipe**: ccx2 cost about half of ccx ($0.129 vs $0.248) and took half the time, but was no more right
   (17/20). The failures, read from the records: the builder tested the function rather than the named command run as
   a process; the builder edited an existing test's asserts; the review graded a silent bug only `[note]`; a run whose
   review failed was reported `ok`; a `--check` that tested nothing (a missing file, a Windows glob).
2. **r5d, the same recipe on the built-in sub-agent**: builtin2 17/20 at $0.114. The lean recipe alone cuts cost and
   also costs correctness (builtin 19/20 → 17/20). So most of ccx2's saving in r5c came from the instruction, not from
   ccx.
3. **r5e, after #129** (sub-agents test through the named entry point and do not edit existing tests; a silent bug is a
   `[must]`; a failed review is not `ok`; a broken check is reported as such): ccx2 19/20, direct 18/20.
4. **r5f, confirmation at the same time**: ccx2 20/20 at $0.116; the original builtin, re-run beside it, 17/20 at $0.202
   (failed q-resume-session twice and quota-stop-log once).

**Where the loop stands**

| Ideal: right 20/20 | met once (r5f) |
| Ideal: cost per success below builtin's $0.155 | met ($0.116–$0.131) |

Where ccx2's time goes (r5e): the builder's own test runs median 50 s / mean 90 s, the review 78 s, fix rounds 114 s,
ccx itself about 1–2 s. #130 (targeted test runs while building, the review running beside the acceptance check) is
merged but not yet measured. Codex's Windows sandbox cannot kill processes, so two `recover` tests fail slowly inside it.

**Caveats**

- n = 20 per run. builtin's right varied 17–19 between days, so a 2-unit gap is within day-to-day noise.
- self was not re-run on the same day as r5e/r5f.
- All tasks come from this repository: Python, Windows.
- ccx2's sub-agent prompt now carries rules builtin's worker does not get (test through the named entry point, do not
  edit existing tests). That is a ccx feature and part of what is measured here, not a like-for-like model comparison;
  builtin2 had the lean recipe but not these rules.
