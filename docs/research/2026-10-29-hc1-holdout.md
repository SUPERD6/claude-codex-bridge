# Hold-out confirmation (hc1): self, built-in sub-agent, ccx on ten tasks not used while building ccx

English · [中文](2026-10-29-hc1-holdout.zh.md) · 2026-10-29 · one pre-registered run, 90 units counted

Earlier: [round 5](2026-10-26-r5.md) (the dev set this run was meant to confirm) and its
[harness audit](2026-10-28-harness-audit.md). The numbers below were checked by two independent fault-finding agents
(one on the numbers, one on the claims) before this page was written; where the raw summary file and this page
differ, this page uses true medians (see §2).

## Result in one paragraph

**By the pre-registered rule, "cheaper at the same correctness" holds, with limits.** On 10 tasks not used while
building ccx (3 rounds, 90 units counted), the three arms showed no distinguishable difference in correctness:
ccx2 29/30, the lead doing it itself 29/30, Claude Code's built-in sub-agent in its default usage 27/28 (the
per-task interval of each difference is about ±3/30). ccx2 cost **$0.063 per success**, about **30 % below** doing it
yourself ($0.090) and about **39 % below** the built-in sub-agent's default usage ($0.103); both paired 95 %
intervals exclude 0. The price is speed: ccx2's median wall time was 61 s, about **3× doing it yourself** (21 s), and
faster than the built-in sub-agent (123 s). Wall time was pre-registered as report-only. On the 5 tasks from
external repositories (the clean ones, see limitation 2) the saving is about **15 % / 42 %**. The built-in arm here is
its default usage with a heavier recipe; the lean builtin2 recipe was not in this run, and on the dev set it was
cheaper than ccx (limitation 1).

Suggested outward wording (keep the qualifiers):

> On 10 hold-out tasks, handing the implementation to Codex through ccx was not seen to be less right than the lead
> doing it itself or Claude Code's built-in sub-agent in its default usage (29/30, 29/30, 27/28), and cost about
> 30 % / 39 % less per success; wall time was about 3× doing it yourself. On the 5 external-repository tasks the
> saving was about 15 % / 42 %.

## 3. Verdict by the pre-registered rules

- **Non-inferiority (the pre-registered pointwise rule)**: ccx2 29 ≥ 29 − 2 → **met**. This is not a statistical
  non-inferiority test: the per-task interval of the difference is about ±3/30, so the data cannot rule out a gap of
  2 or more. We say "not seen to be less right", not "as right".
- **Cheaper**: $0.063 < $0.090 and < $0.103, both paired intervals exclude 0 → **met**.

## 4. Sensitivity: the 2 dropped rows

Two builtin rows were marked env_clean=False: r1 its-timed-fallback-signers (right) and r2 doctor-codex-sandbox
(wrong). Processes, ports and locks were clean; the flag came from the audit's path_hits, which matched text the lead
wrote to the built-in sub-agent: in the first, "Repo: itsdangerous (src/itsdangerous)…"; in the second, the unit's own
temporary folder (under the user's AppData Temp folder). It looks like a false alarm, but the rule was set before the
run, so it is not changed. Counting them (`--include-unclean`): builtin 28/30, $0.105 per success; ccx2 − builtin
−$0.042 (−0.087 to −0.019); the conclusion does not change. Dropping them in fact removed one of builtin's failures.

## 7. Validity and limits (quote them with the numbers)

1. **builtin is the default usage**: builtin's lead was told to read the diff and run the tests, and the haiku
   worker's prompt asked it to run the full `python -m pytest -q`; ccx2 used a targeted `--check` and was told to
   accept a passing check as it is. Part of the price gap comes from the different instructions, not from ccx
   itself. On the dev set, builtin2 (r5d), the built-in sub-agent given the same lean recipe, was 17/20 at
   $0.114 per success, and ccx2 in r5h 19/20 at $0.135 (different runs, not paired, dev set, r5h with CPU
   interference). There was no builtin2 arm in this run, so all we can say is "cheaper than the built-in sub-agent's
   default usage".
2. **This repository's tasks may leak their answers**: the reference answers of this repository's 5 tasks are in the
   ccx code ccx2 runs on (b473976 is later than those changes); Codex's shell reads are not restricted and the audit
   cannot see them; and most of the saving against self comes from these tasks. The 5 external-repository tasks do
   not have this problem; there the saving is −15 % (vs self) / −42 % (vs builtin).
3. **External commits may be memorised**: the external tasks' commits date from 2018-10 to 2026-09; those before the
   models' training cut-off may be remembered, which affects all three arms alike.
4. **Small sample**: 10 tasks, and the 3 rounds are not independent; the per-task intervals are the ones to read.
5. **Only a Sonnet medium lead was tested**; Codex starts at gpt-6-luna low (the save tier; it may climb after a
   failure), and the model each run actually used is not recorded in the result rows.
6. **Amounts are API-equivalent prices** (computed from the price list); Codex actually ran on a subscription.
7. **The harness audit has no data**: it reads each unit's hub, which is cleaned up when the unit ends, so 0 units
   could be audited. The timeline (`r5_timeline`) is available.
8. The postflight recorded one change in the owner's state: the Claude project folder for this working folder went
   1 → 0 (left by an earlier dropped run and cleaned up in this one); the ledger's bytes did not change.
