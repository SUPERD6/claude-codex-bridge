## 1. 怎么测的

- **A/B**：`scripts/eval/seven_ab.py`。4 组对比，每组每个任务 3 轮，每轮里任务顺序和两臂先后都随机（种子 7），同一组同一轮同一任务的两臂是一对，共 72 对、144 个单元。每臂都是全新临时 git 仓库和全新会话。做没做对由隐藏验收测试决定（智能体看不到），结论用 `ccx verify` 记进账本。所有 `ccx run` 带 `--no-ab`，标签 `eval-7c:*`，和正在跑的 H11 一周对比（`ccx trial`）分开。
- **任务**：7 个核心任务（4 个小任务 + 3 个本次新加的中等任务：inventory 改两个文件、csvstats、lru）和 3 个记忆任务（说明里故意不写一条项目约定，隐藏测试检查它）。`tests/test_eval_tasks.py` 确认 15 个任务的起始代码都过不了隐藏测试、参考解都能过。
- **独立实验单元是任务**（核心 n = 7，记忆 n = 3）：每个任务把 3 轮的配对差取平均，再对任务做符号检验和自助法 95% 区间。下面表里没特别说明的区间和 p 都是配对层（n = 21 / 9），只作描述。4 个主检验用 Holm 校正。
- **功能验收**：`scripts/eval/seven_func.py`（codex-lead、resume、undo、budget），每项一个真实场景，按文件和隐藏测试判定。`ccx discuss` 用 main 上的版本单独跑。
- 试跑（`pilot`，8 个单元）发现脚本 bug：写项目记忆前没先 `ccx ctx init`，记忆根本没写进去。修好后正式跑，试跑数据不计入结果。

- 次要比较（不是随机配对的同一组，但同轮同任务）：路由（sonnet）vs 便宜固定模型（(c) 组不审查那一臂，luna low）：做对 21/21 vs 19/21，花费约 **22 倍**（每任务 +$0.045，任务层区间 [+$0.042, +$0.053]，p = 0.016）。也就是说，路由选了“贵而稳”的一档；对这类任务，便宜模型只在 inventory 上错。

### 2.4 (c) 不审查 vs 独立审查（第 4 条）

子智能体 luna low，不升级。审查者由 ccx 自动选：**每次都是 claude sonnet medium**。

| 指标 | 不审 | 审查 | 配对差中位数 [区间] | p（配对 / 任务） |
|---|---|---|---|---|
| 做对 | 19/21（0.71–0.97） | 18/21（0.65–0.95） | 不一致对 1 : 0 对“不审”有利 | McNemar 1.0 |
| 总花费 | $0.0022 | $0.0802 | +$0.078 [+$0.071, +$0.083]（**34 倍**） | <0.001 / 0.016 |
| 总 token | 94,175 | 233,206 | +132,858（2.3 倍） | <0.001 / 0.016 |
| 墙钟时间 | 25.1 秒 | 85.5 秒 | +60.4 秒 | <0.001 / 0.016 |

- 第一次审查有 15/21 次判“有问题”，几乎都是“新行为没有测试”，于是退回修一轮（补测试），第二次全部通过（最终 21/21 “pass”）。**修的那一轮没有把任何一个错的结果变对**（0 次）。
- inventory 三轮都错（同一个 bug：返回 Item 而不是 SKU），审查三次都只要求补测试，没指出这个问题；补的测试按错的行为写，于是“通过”。两臂都错时 ccx 的 check 都是通过的：ccx 说通过但隐藏测试失败，审查臂 3 次、不审臂 2 次。
- 结论：在这类小任务上，现在的审查是“贵的补测试器”，不是找 bug 的。花费里 97% 是审查者（sonnet）本身。

### 2.5 (d) 没有记忆 vs 有项目记忆（第 3 条）

| 任务 | 隐藏测试检查的约定 | 没记忆 | 有记忆 |
|---|---|---|---|
| mem-errors | 报 `errors.AppError`，信息以函数名开头 | 0/3 | 3/3 |
| mem-money | 金额返回整数分 | 0/3 | 3/3 |
| mem-log | 每次调用在 `app` logger 打一行 | 0/3 | 3/3 |

McNemar p = 0.004（9 : 0），Holm 校正后 0.016。代价：每任务多约 $0.0007、多约 2 秒（多读一个文件）。这个效果有一部分是构造出来的（没有记忆就不可能知道约定），它证明的是：**写进 `.ccx/context.md` 的项目记忆，ccx 会指给子智能体，真实子智能体（luna low）会去读、会照做**，3 种约定 9 次全部照做。

没测的：H5 的“建议记下 → 用户同意 → 写进共享记忆”（会写用户真实的 hub，需要用户同意）、hub 的共享记忆经开局 hook 送到 Codex/Claude 子智能体、I6 给没有开局 hook 的工具（Gemini 等）在说明里带记忆（第二轮做）。

## 5. 局限

- **主会话不是真实的**：无头、精简启动、上下文约 1.2 万 token；真实主会话是长对话（中位数 35.2 万 token/请求）、模型是 Opus。第 5 条“省”的金额是外推。
- **任务小**：自己做 3–5 次请求就够，派出去最少 2 次，最多只能省 1–3 次。真实的大任务没测。
- **子智能体只用最便宜的一档**（luna low，本周 Codex 额度限制），路由组的固定臂用 sonnet；更强的子智能体会改变 (a)(c) 的通过率。
- **样本**：独立单元是任务，核心 n = 7、记忆 n = 3；同一任务 3 轮是重复测量。(c) 的“没变好”、(b) 的“没差别”不等于确定没有效果。
- **(d) 的效果部分是构造的**，证明的是送达和照做，不是“记忆让模型更聪明”。
- **墙钟时间**：A/B 跑的同时我在跑功能验收（几分钟），对时间有少量干扰。
- **第 6 条没有对照设计**：需要按时间积累判定，比较早期和后期的预测准确度（Brier 分数），本轮只有 1 天数据。
