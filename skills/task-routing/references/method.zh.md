# 方法：task-routing 怎么定量回答“这个任务用哪个模型”

[English](method.md) · 中文

一句话：**任务难度 vs 模型能力 → 成功率 → 每成功一次的花费 → 在“足够可能成功”的选项里挑最便宜的**，然后每次结果都拿来学习。

## 1. 任务难度 b（0–10）

主智能体按五个看得见的项目打分（细则见 SKILL.md），分数直接相加：

| 项目 | 分数 |
|---|---|
| 改几个文件 | 1 个 → 0 · 2–3 个 → 1 · 4–8 个 → 2 · 9 个以上 → 3 |
| 耦合 | 单个模块 0 · 跨模块 1 · 涉及整体架构 2 |
| 清晰度 | 有规格且有测试 0 · 目标清楚但没测试 1 · 原因/做法未知 2 |
| 风险 | 低 0 · 用户能看到的行为 1 · 关键（安全、数据、正确性、钱）2 |
| 新颖度 | 仓库里有现成写法可照着做 0 · 需要新设计 1 |

这几项参照了可解释智能体路由器使用的画像维度（所需技能/复杂度、对质量的敏感度——Topaz，Okamoto 等 2026），以及 E3（Yin & Feng 2026）“先估计范围”的步骤。等权重只是起点；记录的结果足够多以后，用“结果 ~ 各项分数”的逻辑回归重新拟合权重。

### 1b. 标准单位：人工分钟数（2026-10-24）

打分表的分数是我们自己的尺度。一个通用的尺度是**熟练工程师做这件活要多少分钟**，METR 就用这个单位衡量 AI 智能体（模型有 50% 把握做成的任务长度）。用 `--minutes N` 给出；b = log2(N)，所以 1 分钟是 0、8 分钟是 3、1 小时约 6、17 小时是 10；一个档位有 50% 把握做成的任务长度就是 2^θ 分钟（输出里的 `h50_minutes`）。同时给了打分表时，b = 0.6 × 分钟换算的 b + 0.4 × 打分表的 b。“b = log2(分钟数) 和我们原来的尺度一致”只是一个假设，要等实测结果来检验；Epoch 收录的 METR 实测数据只到 2026 年 4 月，所以新模型的 h50 是由合并后的能力值换算出来的，不是实测值。task-split 技能本来就用同一类曲线来定每块活的大小。

另有两样东西让它更可靠：
- **客观信号**（`ccx/signals.py`）：任务说明里点到、而且确实存在的文件，它们有多少行、跨了几个顶层文件夹、有没有测试提到它们。主智能体没填的打分项（文件数、牵涉几个模块）用它补上；填了的就并排显示，别人重跑得到同样的数字。
- **主智能体的估计偏差**：每记一次结果，这个主智能体的修正值按 0.1 ×（预测 − 实际）变化——它派的活比预测的更常失败，说明它估得太简单，它的 b 就往上调。日志里还记着估计时间和实际时间、打分表各项；有 30 条以上结果时，`task_routing.py refit` 用逻辑回归给出各项权重的建议。只是建议：正在用的权重只有你决定时才改。

## 2. 成功率（项目反应理论 IRT，2PL）

```
P(成功 | 档位 r, 任务 b) = 1 / (1 + exp(-a · (θ_r − b)))
```

- θ_r = 某个档位（智能体 × 模型 × 强度）的能力值，和 b 用同一把 0–10 的尺子。初始值是带日期的估计，写在 `data/priors.toml`。
- a = 斜率（1.2）。θ − b = 0 时成功率 50%；+1.2 约 81%；+2 约 92%。
- IRT-Router（Song 等，ACL 2025）用的是同一思路，在 20 个大模型上学习多维能力和难度。我们用一维版本，因为一个人的记录太少，拟合不了更多参数。

## 3. 一次尝试的花费（API 等价美元）

```
轮数   = 4 + 1.5·b
输入   = 轮数·启动开销 + 上下文 token + 轮数·3000      （其中 85% 是读缓存）
输出   = 1500·(1 + b/2)·强度系数                       （low 0.5，medium 1，high 1.9，xhigh 4，max 13）
美元   = (新输入·输入价 + 读缓存·缓存价 + 输出·输出价) / 1e6
```

- Claude 每轮启动约 4.8 万 token，实测过一次；Codex 的启动开销是暂时的估计。
- 无头启动 `claude -p` 会把这约 4.87 万 token 写进 **1 小时**提示缓存，Anthropic 按输入价的 2 倍收费（5 分钟缓存是 1.25 倍）。在一个很小的 haiku 任务里，这部分约占账单的 90%（2026-10-22 实测）。一小时内再派任务时读缓存只要 0.1 倍，所以集中派任务更便宜。ccx 实测的每次花费（AE$，已计入这项加价）会喂给下面的“成本修正系数”，估算会逐渐贴近真实值。
- 84% 的读缓存中位数来自 Anthropic 对智能体的测量。
- 强度系数来自第三方的 Sonnet 5.5 测试：每个任务 medium $0.59、high $1.12、max $7.67。
- 以上数字在 ccx 记录到真实运行后都会被实测平均值替换。
- 比较时一律用美元，不用原始 token：各家分词器不同，而且缓存 token 便宜 10–40 倍。

## 4. 怎么选：级联还是一次到位

如果能检查成功与否（verifiable），就从便宜的开始，失败了在**同一个会话里**沿同一个智能体的梯子往上升（最多两级）：

```
E[花费 | 从 r 开始] = C_r + (1 − P_r)·C_{r+1} + (1 − P_r)(1 − P_{r+1})·C_{r+2}
P(整条链成功)      = 1 − Π (1 − P_i)
每成功一次的花费    = E[花费] / P(整条链成功)
选择 = 在 P(整条链成功) ≥ τ 的起点里，取“每成功一次的花费”最小的
```

- 从低档开始比从高档开始划算，当且仅当 C_低 < p_低 · C_高（级联规则；FrugalGPT，Chen 等 2023）。例：luna 的价格约是 sol 的 1/20，所以只要 luna 的成功率超过约 5%，先用 luna 就划算。
- Anthropic 的指南提到，“先用低强度，失败了再用高强度重跑”，在通过率相同时大约省 40%。前提是失败能被发现，所以 `--not-verifiable` 会关掉级联。
- 不能检查 → 一次到位：选成功率 ≥ τ 里最便宜的档位。

τ 来自“省钱↔快”旋钮：save 0.70 · balanced 0.80 · fast 0.90（fast 不级联）；也可以给一个数字 k ∈ [0, 1]，τ = 0.70 + 0.20·k，k < 0.75 时级联（balanced = 0.5）。

防护：
- b ≤ 1 → 自己做。
- 最好的链成功率 < 0.5 → 先拆任务（E3：“够用就停”，检查失败了才展开）。

## 5. 自己做还是派出去

```
C_自己 ≈ 自己干活 + 上下文 token · (写入价 + 剩余轮数 · 读取价)    # 读进来的东西之后每一轮都留在上下文里
C_派   ≈ 简报·输出价 + E[子任务花费] + 读回结果 · (写入价 + 剩余轮数 · 读取价)
当 C_派 < 0.85·C_自己 且 P(整条链) ≥ 0.6 时才派
```

## 6. 学习（在线 IRT / Elo 更新）

每次拿到验证过的结果 y ∈ {0, 1}：

```
θ_r ← θ_r + η · (y − P)      η = 0.25
```

学到的偏移量每周向初始值回落一点（×0.95），因为模型和价格都在变。这就是 Elo/Rasch 的在线更新：不需要训练集，只有几次结果时也表现合理。老虎机式路由（MetaLLM、LLM Bandit）和训练出来的路由（RouteLLM）需要几百到几千条标注过的运行。RouterBench 发现，训练出来的路由器往往并不比简单的“成本-质量”混合更好。

### 6b. 用实测结果给新用户起个头（2026-10-25）

新的 hub 什么都没学过，最初的选择只靠手设的 theta。先验里的 `[observed]` 放的是在别处实测的结果——现在是七核心 A/B 第 1 轮：每一档、每个难度（b = 告诉路由的分钟数取 log2），第一档按隐藏测试做对了几次。`observed_offsets` 求出让模型预期的成功次数等于实测（加 ½ 次成功、n+1 平滑，所以 42/42 也是有限值）的 theta 偏移，乘以 `weight`（0.5），最多 `max_shift`（1.5）。它**只在这个 hub 还没记过这一档的结果时**当作偏移；第一次记录就从它开始更新，之后按周衰减回手设先验。已经学过这一档的 hub 不受影响。第 1 轮的结果：luna low +0.67（5 分钟的活 p 从 0.55 到 0.74；实测 38/45），sonnet medium +0.78（42/42）。`ccx doctor --verbose` 的 “routing prior” 一行显示路由从哪里起步。这一轮的任务都是一个人评测用的小 Python 任务，所以权重低。

## 7. 为什么不直接调用现成的路由库

- RouteLLM（lm-sys）和 IRT-Router 发布的路由器是在聊天/问答数据上训练的（Chatbot Arena、MMLU、GSM8K 等）。
- 它们需要嵌入模型或 API 密钥。
- 它们不认识 GPT-6 / Claude 5.5 系列，也没见过智能体写代码这类任务。
- 它们公布的收益是在单次调用的基准上测的：RouteLLM 报告相对“只用 GPT-4”省 35–85%。

我们复用的是它们的**方法**（IRT、级联、每成功一次的花费、帕累托视角），不是训练好的权重。将来如果出现在智能体写代码结果上训练的路由器，可以在同样的接口后面替换第 2 步。

## 8. 校准新档位：DeepSeek（2026-10-24）

新模型刚加入时能力值是猜的。让选模型依赖它之前，先跑几个真实、能自动判对错的任务，用结果定能力值；之后交给第 6 节的在线更新。

deepseek-flash（经 Claude Code，`--bare`，effort low）：在本仓库的临时副本里做 10 个任务，每个任务的检查都在开跑前写好，并确认在没改过的副本上判为不通过：加文档字符串、加一个测试、修一个预埋的 bug（有失败的测试，b 2）、按说明写新函数并加测试（b 3）、加类型标注、一个只读问题、提取常量、写一行 CHANGELOG、修一个跨模块的预埋记账 bug（b 5）、加一个命令行开关并加测试（b 4）。结果：10 个全部一次通过；按高峰价合计 $0.054（当天是闲时，实际约一半）；每个 11–202 秒。先验取 N(3.5, 1.5²) 时后验众数 5.3（80% 区间 4.3–6.8）；先验取 2.5 / 4.5 时是 5.0 / 5.75。最初取 **4.5**，即区间低端，因为任务小、又是我们自己挑的。有了公开评测（第 10 节）以后，手设值改回一个猜测（3.5），十次结果作为普通的实测结果记进学习状态，用来修正评测换算出的能力值，而不是取代它（修正 +0.83）。v4-pro 一次都没用上（没有失败可升档）。十次成功说明不了它从哪里开始会失败。

## 9. 公开评测数据（每周更新）

`task_routing.py refresh`（或 `ccx bench refresh`）把三个开源来源下载到学习状态旁边的 `benchmarks.json`；配合 ccx 使用时，开局发现数据满一周就在一个独立的后台进程里自动更新（失败的来源 6 小时后再试；没联网就继续用旧数据）。数据不会被转发出去。

| 来源 | 内容 | 许可 |
|---|---|---|
| Epoch AI，epoch.ai/benchmarks | 综合能力指数 ECI（带区间）、GPQA Diamond、SWE-bench Verified、SimpleQA Verified；转载的 FrontierCode 和 Terminal-Bench（按工具和思考强度）、METR 时间跨度、WebDev Arena、HLE | Epoch 自测数据和 ECI 是 CC BY 4.0；`_external` 文件保留各自的许可 |
| LMArena，huggingface.co/datasets/lmarena-ai/leaderboard-dataset | 真人评分：对话、事实准确度、智能体任务做没做成、乱编工具调用、bash 可靠性、搜索事实准确度 | CC BY 4.0 |
| models.dev | 每百万 token 的价格、长提示词的高价档 | MIT |

展示它们的数字时要注明出处（`task_routing.py sources` 会打印出处）。模型名保持各来源自己的写法；第 10 节（合并）负责把它们对应到档位。Artificial Analysis 不在默认来源里：它的条款禁止抓网页，免费接口只限用户自己内部使用，所以只能由用户用自己的密钥在本机接入。

**你自己的来源。** 在 `<状态目录>/bench-sources/` 里放一个 `*.py`，写上 `NAME`、`CREDIT` 和返回评测行的 `fetch(get)`，可选 `available()` 和 `KIND_WEIGHTS {类型: {评测: 权重}}`，就会和其他来源一起拉取、一起合并。它只在你的电脑上，适合放那些条款只允许你自己使用的数据（比如用你自己密钥的 Artificial Analysis）。还没配置好的来源（`available()` 为假）会被跳过，不算失败。

## 10. 把评测合并成能力值

`scripts/merge.py`；只要有缓存，`route`、`three_way` 和 `record` 都会用它：

1. **把数据行对到档位。** 每个来源的模型名先拆出思考强度，再只留字母和数字（“claude-haiku-5-5_max”“Claude Haiku 5.5 (High)” → `claudehaiku55`，max / high）。先验里的 `[aliases]` 把每个档位的模型对应到这些名字，完全同一版本权重 1，旧版本更低。没写思考强度的行，当作该模型的最好设置（max）。
2. **每个评测各给一个估计。** 在“锚点”上拟合一条直线：评测分 → 能力值。锚点是版本完全对得上的 Claude 和 Codex 档位，它们的手设能力值按思考强度换算表移到这一行的强度上（max 0、xhigh −0.3、high −0.8、medium −1.5、low −2.8，手设的整数值，之后要重新拟合）。锚点少于 4 个或直线不是上升的，就跳过这个评测。每个对上的档位都从直线上读出能力值，再移回自己的强度。
3. **合并。** 权重 = 这个评测对这类活的相关程度 ÷ 拟合误差的平方；版本或强度对不上的减半；单个评测最多占一半。活分四类：`code`（FrontierCode、SWE-bench Verified、Terminal-Bench、LMArena 的智能体任务和 bash 可靠性、ECI……）、`read`（ECI、GPQA、HLE……）、`research`（SimpleQA、LMArena 的事实准确度……）、`write`（LMArena 对话、ECI……）。类型来自 `--kind`，没给时只读任务算 `read`，其余算 `code`。
4. **和手设值合并**（手设值的标准差取 1.5），按方差倒数加权；实测结果学到的修正值加在上面，按 `code` 的合并结果来学。

第一次运行（2026-10-24，code）：GPT-6 Astra max 9.2 → 7.9，Sol medium 5.5 → 6.3，Opus max 9.0 → 8.5，DeepSeek flash low 在计入本地结果前 4.5 → 2.5；低强度的 Haiku 和 luna 在 2.2–2.8 附近。

## 11. 按总代价选（2026-10-24）

真钱和额度不是同一种“货币”，时间和风险也要算。每个选项（一个起始档位加它的升档链、主智能体自己做、主智能体自带的子智能体）都折算成一个美元数：

- **真钱**——按 token 付费的智能体（`[cash]`，比如 DeepSeek）：它的预计 API 花费；
- **额度**——订阅制的智能体：预计的 API 等价花费 × λ，即额度的“隐形价格”。窗口还有余量时 λ 是 0.3（额度值得留给主智能体和难的活），用到 60%–100% 之间线性涨到 1.0，超过就是 2.0。主智能体自己做、它自带的子智能体、写说明/读结果/检查的开销，都用主智能体自己的额度；
- **时间**——预计分钟数（这个档位有实测记录后用实测，否则按思考强度和难度估）× 每分钟的价值：省钱模式 $0.005、平衡 $0.02、赶时间 $0.10；
- **风险**——整条升档链仍然失败的概率 × 做错一次的代价：低风险 $0.5、用户看得见 $3、关键 $20。主智能体自己做时，算上它自己检查并重做一次。

**“用掉多少”指的是推算值（ccx，`ccx quota`）。** 计算 λ 用的不是现在用掉的比例，而是到重置时会用掉的比例：只看当前窗口（重置时间往后跳、或用量突然下降，就算新窗口——换套餐两种情况都会发生），用最近 48 小时的速度推算到重置；读数不到 6 小时，就太早推算，直接用当前比例。每个窗口都算（Claude 的 5 小时和 7 天；Codex 的周额度，以及有些套餐的 5 小时），以最紧的那个为准。Codex 的读数每次调用都从它自己的日志里读；Claude 的只出现在 Claude 子任务的返回里，所以 ccx 会把它们存下来；最新一条超过 1 小时、而这次又可能用 Claude 时，就发一个很小的请求去读。

在升档链能达到成功率目标的选项里，选总代价最低的（和主智能体自己做的差距在 15% 以内时留给它）。按 token 付费的智能体不再用额度门槛挡着：它花的真钱直接和额度的隐形价格比；每天的花费上限照旧。这些数字都是脚本里的默认值，可以在先验里改。

## 局限（要明说）

- 记录到结果之前，初始值只是估计，前几周没有校准。
- 打分是粗略的一维概括；两个 b 相同的任务可能差别很大。
- 成本估计误差约 ±2 倍，直到被实测平均值替换。
- “成功”指检查通过；检查本身不严，结论也就不严。
